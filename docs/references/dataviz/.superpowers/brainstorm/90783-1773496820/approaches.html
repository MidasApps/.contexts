3 Abordagens de Arquitetura Multi-Agent

Compare as arquiteturas e clique na que preferir

A

prepareStep Router

Um unico streamText com prepareStep dinamico

Arquitetura
useChat (frontend)
|
POST /api/chat
|
streamText + prepareStep()
| decide activeTools + system por step
SQL Tools Business Tools Dashboard Tools Compare Tools External Tools Export Tools Simulation Tools

Pros

  • Um unico stream — UX fluida, sem handoff
  • 100% nativo do AI SDK v6
  • prepareStep troca modelo/tools/prompt por step
  • Simples de implementar e debugar

Cons

  • O modelo "orquestrador" e o "especialista" sao o mesmo LLM
  • System prompt pode ficar muito longo com 7 agentes
  • Todas as tools competem por atencao do modelo
  • Dificil ter engenharia de contexto especializada por agente
B

Orchestrator + generateText Sub-Agents

streamText orquestra, generateText executa sub-agentes internamente

Arquitetura
useChat (frontend)
|
POST /api/chat
|
streamText (Orchestrator)
tools: route_to_sql, route_to_business, route_to_dashboard...
| tool.execute() chama generateText()

generateText

sql_execute tool

generateText

glossario context
indicadores tool
Dashboard Agent
generateText
Flash-Lite
dashboard state
filter tools
Compare
Pro model
External
Flash model
Export
Flash-Lite
Simulation
Pro model

Pros

  • Cada agente tem seu proprio modelo, system prompt e tools
  • Engenharia de contexto 100% especializada por agente
  • Orquestrador leve (Flash-Lite) roteia, especialistas (Pro) executam
  • Sub-agentes podem ter multi-step proprio (stopWhen interno)
  • 100% compativel com AI SDK — tools retornam resultado do generateText

Cons

  • Latencia: 2+ chamadas LLM por pergunta (orquestrador + agente)
  • Mais complexo de implementar que A
  • Sub-agentes nao fazem streaming (generateText bloqueia)
C

Orchestrator streamText + Sub-Agent streamText (nested streaming)

streamText orquestra, tools disparam sub-streamText com resultados parciais

Arquitetura
useChat (frontend)
|
POST /api/chat
|
streamText (Orchestrator - Flash-Lite)
tools com preliminary results (yield)
| tool.execute() e um async generator
SQL Agent (Pro)
1. yield {status: "analyzing"}
2. generateText → SQL
3. yield {status: "querying", sql}
4. Execute BigQuery
5. yield {status: "done", rows}
6. return final result
Simulation Agent (Pro)
1. yield {status: "planning"}
2. generateText → scenario
3. yield {status: "computing"}
4. Run calculations
5. yield {status: "done", results}
6. return final result
Frontend recebe preliminary results em tempo real via tool-result stream

Pros

  • Tudo do B + feedback em tempo real ao usuario
  • Preliminary tool results (yield) mostram progresso passo a passo
  • Cada agente e independente com seu modelo e contexto
  • UX premium: usuario ve "Analisando pergunta..." → "Gerando SQL..." → "Executando query..." → resultado
  • 100% AI SDK v6 nativo (preliminary results e feature documentada)

Cons

  • Mais complexo de implementar (async generators)
  • Mesma latencia do B (2+ chamadas LLM)
  • Precisa de UI no frontend para renderizar cada status

Minha Recomendacao: Opcao C

A opcao C combina o melhor dos dois mundos: isolamento total de contexto por agente (cada um com seu modelo, prompt e tools) com feedback progressivo ao usuario via preliminary tool results. O usuario ve exatamente o que esta acontecendo ("Gerando SQL...", "Executando query...", "Analisando resultados...") enquanto o agente trabalha. A complexidade extra dos async generators e gerenciavel e o AI SDK v6 suporta nativamente.
