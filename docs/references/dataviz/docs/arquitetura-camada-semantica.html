Como o Liquid DataViz resolve dados

Templates → Métricas (contrato de KPI) → Data Contract (contrato de dados) → Client binding → BigQuery. Este doc é o meu entendimento da arquitetura, pra você conferir se estou certo. Termino com onde a BRZ está e o que falta.

1. As 5 camadas

A arquitetura desacopla o que um dado significa (vocabulário canônico) de como cada cliente o armazena (colunas reais). De baixo (físico) para cima (empacotamento) e o tenant que amarra tudo:

PHYSICAL Data Source — o BigQuery real (projeto.dataset.tabela). Colunas com os nomes que o cliente tem de fato.
▲ binding mapeia coluna real → atributo canônico
SEMANTIC · global Data Contract — dataContracts/{id}/entities/{e}/attributes/{a}.
Vocabulário canônico: entidades (ex.: contratos) e atributos (ex.: saldo_devedor, rating_liquid) com label/tipo/unidade. Autoridade única, sem duplicação. Hoje existem: liquid-play, liquid-play-plus, external.
SEMANTIC · global Metric Catalog — metrics/{domain.slug} (105 hoje). É o "contrato de KPI".
requires[] = atributos exigidos, fully-qualified contractId.entity.attribute. recipe = receita executável (aggregation ou sql) escrita em refs curtos entity.attribute. Uma métrica é reusável por vários produtos.
▲ produto referencia (não duplica)
PACKAGING Product — products/{id}. Empacotamento comercial: contractRefs, entityRefs, metricRefs, routes.
Ex.: "Liquid Play+ Credit". Não carrega schema próprio — só aponta para contract + métricas.
▲ cliente assina produtos e faz o de-para
TENANT Client — clients/{id}.productBindings[]. Onde a teoria encontra os dados do cliente.
Cada binding: productId → datasets[]. Cada dataset tem contractRef (qual contrato ele cobre) e schemaBindings: mapa flat "entity.attribute" → coluna_real | null.
Template (o que você importa) é uma página de dashboard: blockMap + layout + metricRefs[]. Cada bloco (KPI/chart/table) referencia uma métrica do catálogo. Importar um template cria um relatório (página) com esses blocos; abrir a página dispara a resolução de dados de cada métrica.

2. Dois caminhos de dados (por que o dashboard funciona e o template não)

Legado — direto

/api/bigquery + queries.ts (SQL hardcoded contra o schema do cliente).

  • Usado pelas páginas fixas (Visão Geral, Contratos, PDD…).
  • Não passa pela camada semântica.
  • É por isso que o dashboard da BRZ carrega (36.042 contratos etc.).

Semântico — por métrica

/api/metrics/[id]/data + resolveMetric().

  • Usado pelos blocos de template importado.
  • Exige contract + schemaBindings mapeados.
  • É aqui que a BRZ falha — config semântica incompleta.

3. Fluxo de resolução de uma métrica

Quando um bloco do template precisa de dados (fetchMetricData → POST /api/metrics/[id]/data com {clientId, productId, pageFilters}):

  1. Carrega a métrica de metrics/{id}. Sem recipe → não é executável.
  2. Descobre o contrato: metricContractId = requires[0].split('.')[0] (ex.: liquid-play).
  3. Acha o dataset do cliente cujo contractRef === metricContractId, varrendo os productBindings. se nenhum cobre → 422 "Nenhum dataset cobre o contrato"
  4. Resolve cada ref do recipe (entity.attribute) para a coluna real via resolveColumn(binding, ref) (tabela abaixo).
  5. Monta o SQL com identificadores sanitizados e valores em params nomeados (@x), roda no BigQuery e devolve as linhas para o bloco.

4. As regras do resolveColumn (o ponto crítico)

Para cada atributo que a métrica precisa, o servidor olha schemaBindings["entity.attribute"] do dataset do cliente:

Situação no schemaBindingsComportamentoResultado p/ a métrica
Mapeado p/ string (ex.: "saldo_devedor")Usa coluna_real AS attributeOK
Mapeado p/ nullCliente declarou o atributo indisponívelmétrica desabilitada (empty state)
Ausente + cliente "migrado" (schemaBindings não-vazio)FAIL-LOUD — não adivinha a coluna (evitaria rodar SQL contra coluna inexistente)422 "sem mapping em schemaBindings"
Ausente + cliente legado (schemaBindings vazio)Back-compat: assume o nome do atributo como coluna (+ console.warn)tenta, sob risco

Nuance importante: a ADR-0015 (status Proposed) propõe na regra 3 "atributo sem binding → assume o nome". A implementação refinou isso: só cliente legado (schemaBindings vazio) faz esse fallback; cliente já migrado falha-cedo. Minha leitura: "refs de catálogo são soft+warning; só resolveColumn (dados) é fail-loud". É proposital — não rodar SQL contra colunas erradas em risco de crédito.

5. Onde a BRZ está hoje (diagnóstico)

A BRZ tem productBindings (credit, play-legacy) mas a camada semântica está quase vazia:

ItemEstado encontrado
contractRef dos datasetsera "canonical" — o default do schema (Slug.default('canonical')), mas não existe contrato "canonical"; os reais são liquid-play/liquid-play-pluscorrigi → liquid-play
schemaBindingsmapeia só 2 atributos: contratos.data_base_report, contratos.saldo_devedorincompleto
schema semântico detectadosó 2 colunas, 1 entidade (contratos); sem rating_liquid etc.não sincronizado
métricas dos templatesexigem dezenas de atributos do contrato liquid-playnão cobertos

Como o schemaBindings não está vazio, a BRZ é tratada como "migrada" → qualquer atributo não mapeado dá fail-loud. Foi exatamente o erro: Attribute "contratos.rating_liquid" sem mapping.

6. O que falta para a BRZ funcionar "conforme a arquitetura"

  1. Sincronizar o schema da BRZ — detectar (via INFORMATION_SCHEMA / /api/schema-detect) todas as colunas/tabelas reais dela.
  2. Completar o schemaBindings — mapear cada entity.attribute que as métricas dos templates usam → coluna real da BRZ. Atributos que a BRZ genuinamente não tem → null (a métrica se desabilita com empty state, em vez de quebrar).
  3. Conferir o contractRef por binding — apontar para o contrato certo (liquid-play e/ou liquid-play-plus) conforme o produto.

Ferramentas previstas para isso: Admin → Data Contracts + Schema Map editor + detecção de schema. Eu não chuto os mapeamentos (adivinhar rodaria SQL contra coluna errada — o que o fail-loud existe pra impedir); preciso casar os atributos do contrato com as colunas reais da BRZ.
