Liquid DataViz — Documentação de Produto: da configuração do cliente aos indicadores

Data de geração: 21 de julho de 2026

Propósito: documentação de referência para revisão de coerência das funcionalidades.

Escopo: pipeline completo cliente → bases → contratos de dados → métricas → templates → reports → visualização, mais a camada de IA (agentes, memória, evals). Idioma: PT-BR.

#Introdução e arquitetura geral

O Liquid DataViz é uma plataforma de business intelligence multi-tenant para visualização e análise de dados de securitização de crédito imobiliário. Uma única aplicação Next.js 16 (App Router) atende vários clientes (organizações assinantes) — os quatro legados OM, BRZ, CONX, IMCASA e os novos no modelo multi-produto como Galli e Vila Rosa. A configuração, os metadados, as permissões e toda a camada de IA vivem no Firestore (ADR-0013); o BigQuery guarda exclusivamente os datasets de negócio de cada cliente (carteira, contratos, pagamentos, covenants). O isolamento entre clientes é responsabilidade do código da aplicação, com falha fechada (fail-closed) e clientId server-bound (ADR-0006).

O coração do produto é uma camada semântica em cinco níveis (ADR-0015) que desacopla "o que medir" de "onde estão os dados". O pipeline vai de ponta a ponta: o cliente declara productBindings ligando produtos a datasets BigQuery; cada Data Contract define o vocabulário canônico de entidades e atributos; as métricas (indicadores) declaram o que calcular em entidade.atributo abstrato e viram SQL parametrizado via recipes (aggregation, sql, derived); os templates montam dashboards a partir de blocos (canvas em grade de 6 colunas com blockMap + layout); os reports por cliente são cópias concretas dos templates; e a visualização em runtime é preenchida por useReportData, que faz POST /api/metrics/batch e resolve cada bloco contra o binding do cliente.

Paralelamente, uma camada de IA multi-agente serve duas superfícies: o orquestrador analítico (chat conversacional na AISidebar, via /api/chat, em migração para o runtime Mastra) e o canvas orchestrator (construção de dashboards no modo edição, via /api/canvas-chat). Ambos compartilham ~57 tools, um registry de modelos Vertex (Gemini) em quatro tiers, e um substrato de memória/RAG sobre Firestore (working memory, embeddings, catálogo SQL curado, evals e drift de judge). A configuração dos agentes é data-driven via AI Studio (ADR-0016/0017), com baseline em código como fallback.

Esta é uma documentação de referência para revisão de coerência das funcionalidades. O propósito é servir de base para revisar incoerências entre documentação e implementação, e entre caminhos paralelos do código — por isso cada afirmação preserva sua referência arquivo.ts:linha. As seções abaixo cobrem o pipeline completo; o Apêndice A consolida todas as observações e possíveis inconsistências levantadas, com severidade atribuída para priorização.

#Cadastro de cliente, autenticação e multi-tenancy

#Visão geral

O liquid-dataviz é um dashboard multi-tenant: uma única aplicação Next.js atende vários clientes (organizações assinantes) — os quatro legados OM, BRZ, CONX, IMCASA e os novos no modelo multi-produto como Galli e Vila Rosa. Cada cliente é um documento na coleção Firestore clients, e todo o isolamento entre clientes (quem vê o quê) é responsabilidade do código da aplicação, não do banco — princípio formalizado na ADR-0006 (adrs/decisions/0006-multi-tenancy-strict-isolation.md). O storage canônico de configuração/metadados/permissões é Firestore (ADR-0013); o BigQuery guarda apenas os datasets de dados de cada cliente.

O modelo de dados do cliente está em transição. Convivem dois formatos no mesmo documento: o legado (campo dataset string único + schema flat) e o novo (productBindings[], onde cada binding liga um productId a um ou mais datasets BigQuery via contractRef + schemaBindings). Leitores devem preferir productBindings quando presente (src/shared/schemas/client.ts:5-12). Os clientes seedados originalmente (scripts/seed-firestore.mjs:26-55) usam o formato legado; os clientes novos (Galli, Vila Rosa) e a UI de administração usam exclusivamente productBindings.

Autenticação é Firebase Auth (Google popup ou e-mail/senha) no front, e validação de token via Firebase Admin SDK nas rotas de API. Autorização tem três camadas: acesso ao cliente (tenant), acesso à rota (página) e escopo de dataset — todas aplicadas server-side com falha fechada (fail-closed). Usuários com e-mail no domínio askliquid.com são tratados como admin e ignoram (bypass) todas as checagens de permissão (src/shared/lib/runtime-config.ts:32-35).

#Modelo de dados do cliente (Firestore clients)

#O que faz

Cada documento clients/{clientId} descreve uma organização assinante: identidade visual (nome, inicial, cor) e o mapeamento para os dados BigQuery que ela consome. O id do documento é um slug kebab-case (ex.: vila-rosa) e serve como clientId em todo o sistema.

#Seleção de cliente na aplicação

#O que faz

Determina qual cliente está ativo, persiste a escolha e os filtros por cliente, e descobre a lista de clientes que o usuário pode ver.

#Fluxo

  1. useClients() (src/shared/hooks/useClients.ts) roda no layout, escuta onAuthStateChanged e busca GET /api/clients com o token do usuário (useClients.ts:21-24,102-125). Faz polling a cada 30s (useClients.ts:83,122-124) e só re-seta o store quando os dados mudam de fato (guard de comparação JSON, useClients.ts:50-59).
  2. GET /api/clients (app/api/clients/route.ts:21-44) retorna apenas os clientes que o usuário pode ver: admin recebe todos; não-admin recebe só os clientId presentes no seu clientAccess (clients/route.ts:9-19,32-38).
  3. setClients() no store (app-store.ts:255-268) escolhe o cliente ativo: mantém o salvo em localStorage (liquid:activeClientId) se ainda existir, senão usa o primeiro da lista; limpa o cache de queries (app-store.ts:256,259-264).
  4. getActiveClient() resolve o cliente ativo (app-store.ts:250-253).
  5. Trocar de cliente: switchClient(clientId, currentFilters) salva o ativo, zera grupo/report ativos e preserva os filtros do cliente anterior por cliente (app-store.ts:332-344). Filtros por cliente vivem em clientFilters (app-store.ts:91,346-348), com defaults em DEFAULT_FILTERS (app-store.ts:43-55).

#Permissões e multi-tenancy fail-closed

#Modelo (ADR-0006)

clientId é server-bound: derivado do token de auth e cruzado com as permissões do usuário; nunca aceito cru de body/query sem validação, e nunca exposto ao modelo de IA como input editável (adrs/decisions/0006-multi-tenancy-strict-isolation.md:62-92). clientId ausente em qualquer ponto faz a operação falhar fechada com erro tipado, sem fallback "global" (ADR-0006 §8, linhas 142-146). A ADR cita RAG/memory/BQML/cache; esta seção documenta o enforcement equivalente nas rotas de dados.

#Camadas de autorização (server-side)

Todas em src/shared/lib/api-auth.ts; admin (isAdminEmail) faz bypass em todas.

  1. Acesso ao cliente (tenant) — verifyClientAccess(email, clientId) (api-auth.ts:182-207): confirma que o clientId está no clientAccess do usuário. Impede IDOR cross-tenant em rotas que recebem clientId de body/query (ex.: app/api/report-groups/route.ts:19-22,57-60).
  2. Acesso ao dataset — verifyDatasetAccess(email, dataset, clientId?) (api-auth.ts:88-169). Dois caminhos:
    • Com clientId (preferido, api-auth.ts:104-140): carrega clients/{clientId}, confirma que o dataset pertence ao cliente (campo legado dataset ou algum productBindings[].datasets[].datasetId), e cruza com o clientAccess do usuário.
    • Sem clientId (back-compat, api-auth.ts:142-168): localiza o cliente por where('dataset','==',dataset). Fail-closed: se nenhum cliente reivindica o dataset, nega (api-auth.ts:157-159) — comentário registra que antes datasets "órfãos" eram liberados (vazamento cross-tenant), corrigido por ADR-0006.
  3. Acesso à rota (página) — verifyRouteAccess(email, clientId, route) (api-auth.ts:218-255): aplica no servidor a mesma lógica dos hooks da UI (routeOverrides do cliente > rotas dos grupos), via canAccessRoute puro (src/shared/lib/permissions/authorize.ts:35-49). Comentário nota que sem isso a permissão fina era "apenas cosmética" (G1 da auditoria).

#Mapa métrica → rota

src/shared/lib/permissions/metric-route-map.ts mapeia cada métrica à página que ela serve (metric-route-map.ts:15-155). Em executeMetric, se a métrica tem rota, exige verifyRouteAccess antes de executar (execute-metric.ts:147-154); métricas compartilhadas entre páginas retornam null e ficam só com o tenant-check (metric-route-map.ts:5-13,157-159). Todas as métricas covenants.* (Vila Rosa) mapeiam para a rota /g (metric-route-map.ts:74-155).

#Enforcement na execução de métrica

executeMetric (src/shared/lib/metrics/execute-metric.ts:118-259) aplica, em ordem:

  1. Propriedade: métrica com ownerClientId não-nulo só executa no próprio cliente (execute-metric.ts:137-141).
  2. Rota (via mapa acima, execute-metric.ts:147-154).
  3. Resolução por contrato: o dataset é escolhido pelo contractRef igual ao prefixo de metric.requires[0] (single-contract, execute-metric.ts:210-224) ou pelos contratos das refs (derived, execute-metric.ts:157-197). Se o cliente não cobre o contrato exigido → falha 422 (execute-metric.ts:183,224).
  4. Tenant/dataset: verifyDatasetAccess por dataset resolvido (execute-metric.ts:185-186,234-235).
  5. Cobertura: atributos exigidos ausentes no binding → falha 422 com missing[] (execute-metric.ts:240-245).
  6. Erros de BQ/Firestore viram 500 genérico, sem vazar SQL/topologia (execute-metric.ts:254-258).

Rota que orquestra: app/api/metrics/[id]/data/route.ts (single) e /api/metrics/batch (bulk, compartilha execute-metric.ts).

Referência concreta: onboarding do Vila Rosa (branch atual). O fluxo abaixo é a espinha dorsal para cadastrar um cliente novo até funcionar. Hoje ele é majoritariamente via scripts de seed, não pela UI (ver Observações).

#Pré-requisitos (fundações no Firestore)

  1. DataSource BigQuery cadastrada (ex.: bq-data-wh) — coleção dataSources, consumida por getDataSource (execute-metric.ts:71-77,191-192).

  3. Product cadastrado (coleção products) com metricRefs[], indicators[], routes[] (src/shared/schemas/product.ts:67-78). No caso Vila Rosa, os produtos são liquid-play e liquid-play-plus.
  4. Métricas publicadas (coleção metrics) e relações (coleção relations).
  5. Templates de dashboard publicados (coleção dashboardTemplates) para gerar os reports.

#Passo a passo (protocolo de seeds da casa)

  1. Seedar as métricas do domínio. scripts/seed-covenants-v2-metrics.mjs grava as ~64 métricas covenants.* (definições em scripts/metrics/covenants-v2.mjs), com validação de shape manual que espelha src/shared/schemas/metric.ts (seed-covenants-v2-metrics.mjs:40-52).

  3. Cadastrar o cliente + bindings + merge de métricas no produto. scripts/seed-vila-rosa-client.mjs:
    • Cria clients/vila-rosa com dois productBindings (seed-vila-rosa-client.mjs:213-244): liquid-play → dataset vila_rosa_monitor (contratos, fluxo_caixa, pagamentos) e liquid-play-plus → dataset vila_rosa_covenants (7 entidades). schemaBindings são gerados 1:1 (coluna = atributo) a partir dos schemas transcritos do BigQuery (buildIdentitySchemaBindings, linhas 199-205).
    • contractRef = productId em cada binding (linhas 222,235) — decisão deliberada (ver Observações / divergência de brief nas linhas 17-46): executeMetric resolve o dataset pelo contractRef igual ao prefixo de requires[0], não pelo productId (execute-metric.ts:210); usar contractRef: 'canonical' faria toda métrica falhar 422.
    • Faz merge das novas métricas em products/liquid-play-plus.metricRefs (seed-vila-rosa-client.mjs:300-325) — é isso que "surfaça" as métricas para o cliente (via enabledIndicators: null, ver abaixo).
  4. Criar o grupo de reports + os reports a partir dos templates. scripts/seed-vila-rosa-reports.mjs:
    • Cria clients/vila-rosa/groups/covenants (grupo de navegação, name+order, linhas 138-165) e 13 reports em clients/vila-rosa/groups/covenants/reports/{slug} (linhas 61-75,167-203).

    • Verificação pós-apply confere blockMap não-vazio e o token de drill-through (seed-vila-rosa-reports.mjs:205-249).
  5. Dar acesso aos usuários. Adicionar {clientId: 'vila-rosa', routeOverrides: ...} ao clientAccess de cada usuário externo, via UserForm/POST /api/users (ou seed). Usuários internos @askliquid.com são admin e já têm acesso a tudo.

#Protocolo dry-run → apply → force (guarda anti-sobrescrita)

Todos os seeds seguem o mesmo protocolo (seed-vila-rosa-client.mjs:64-71,256-298, seed-vila-rosa-reports.mjs:40-47,138-203):

  1. --dry-run: mostra o que faria, não grava nada (obrigatório especificar --dry-run ou --apply, senão exit(2)).
  2. --apply: grava. Para cada doc, compara o conteúdo desejado com o existente via stableStringify (JSON determinístico com chaves ordenadas, ignorando timestamps).
    • Idêntico → no-op ("já existe, conteúdo idêntico").
    • Diferente e sem --force → CONFLITO: pulado, NADA gravado (proteção contra sobrescrever doc de outro cliente/pipeline).
    • Diferente e com --force → sobrescreve, preservando createdAt.
  3. Re-rodar --dry-run/--apply após aplicar deve reportar tudo como no-op (idempotência). Documentado como boa prática (dry-run → apply → re-dry-run).

O molde vivo desse protocolo é scripts/seed-liquid-play-contracts.mjs (cliente Galli), citado como referência em seed-vila-rosa-client.mjs:9,196.

#Observações e possíveis inconsistências

Fatos observados no código que podem indicar incoerência para revisão. Cada um com referência.

  1. /api/bigquery não existe mais, mas ainda é citado como fonte. O CLAUDE.md descreve o data flow como "POST to /api/bigquery" (seção Data Flow), e vários tipos comentam "@deprecated legado do caminho /api/bigquery — G9" (src/features/admin/model/types.ts:4,15). Não existe diretório app/api/bigquery/ (confirmado por listagem de app/api/). O caminho de dados atual é a camada semântica: app/api/metrics/[id]/data/route.ts e /api/metrics/batch, via src/shared/lib/metrics/execute-metric.ts. Documentação (CLAUDE.md) está defasada em relação ao código.

  2. Rotas /g (reports dinâmicos) e /explore não são concedíveis pela Admin UI. Todas as métricas covenants.* do Vila Rosa mapeiam para a rota /g (metric-route-map.ts:74-155), e verifyRouteAccess exige /g no acesso do usuário (execute-metric.ts:147-154). Porém /g não está em ALL_ROUTES (src/features/admin/model/types.ts:55-70), e /explore está em ALL_ROUTES (linha 66, grupo IA) mas o RouteCheckboxGrid só renderiza os grupos Carteira/Risco/Operacional/Anexos (RouteCheckboxGrid.tsx:11), omitindo IA. Consequência: um usuário não-admin não tem como receber acesso a /g nem a /explore pela UI (nem via grupo, nem via routeOverrides). Como o produto inteiro do Vila Rosa vive em /g, apenas usuários @askliquid.com (admin, bypass) conseguem ver os reports; clientes externos ficariam bloqueados a menos que routeOverrides seja editado fora da UI (script/console).

  3. Granularidade divergente da checagem de rota /g entre cliente e servidor. Server-side, verifyRouteAccess checa a rota /g (do routeForMetric, execute-metric.ts:150). Client-side, ProtectedRoute checa o pathname completo (ex.: /g/covenants/r/visao-executiva) contra baseRoutes/routeOverrides (ProtectedRoute.tsx:25,67; sem requiredPath no DashboardLayout.tsx:70,80), que contêm apenas caminhos de página (/dashboard, etc.). Para não-admin as duas checagens falham (com granularidades diferentes); só admin passa. As duas camadas não comparam a mesma string.

  4. Bypass de auth em dev promove requests não autenticados a admin. Com NODE_ENV=development e FIREBASE_ADMIN_PRIVATE_KEY ausente (entre outras condições), verifyAuthToken retorna dev@askliquid.com quando não há Bearer token válido (api-auth.ts:47-49,66-68; runtime-config.ts:37-45). Esse e-mail é admin (runtime-config.ts:32-35), então toda rota de API responde como admin sem autenticação nesse modo. É intencional para DX local, mas é um fail-open — depende estritamente de NODE_ENV.

  5. Embedded mode concede admin total. Em iframe com token do shell pai, isAdmin vira true incondicionalmente (useUserPermissions.tsx:43-45), e ProtectedRoute libera todos os filhos sem checar permissão (ProtectedRoute.tsx:61). O isolamento passa a depender inteiramente do shell pai, não das permissões do usuário no Firestore.

  6. Formato legado e novo coexistem, mas a UI só produz o novo. POST /api/clients aceita ambos (dataset exigido só sem productBindings, clients/route.ts:83-86), e verifyDatasetAccess/matchClientDataset cobrem ambos. Porém o ClientForm exige ≥1 binding (ClientForm.tsx:104-107) e não expõe o campo dataset. Os 4 clientes legados (om/brz/conx/imcasa) foram criados só com dataset (seed-firestore.mjs:26-55,107-115); editá-los pela UI força adicionar bindings (não há caminho de UI para gerenciar o dataset legado). Migração incompleta.

  7. Dois conceitos distintos chamados "grupo". Coleção raiz groups = grupos de permissão/RBAC ({name, description, routes[]}, admin-only via /api/groups, groups/route.ts:20-27). Subcoleção clients/{id}/groups = grupos de navegação de reports ({name, order}, com subcoleção reports, via /api/report-groups que usa verifyClientAccess e não é admin-only, report-groups/route.ts:19-38; seed-vila-rosa-reports.mjs:138-165). Mesmo termo, coleções e semânticas diferentes — fonte provável de confusão.

  8. enabledIndicators gateia surfacing, não execução. O campo ClientProductBinding.enabledIndicators (client-binding.ts:77) é aplicado como interseção apenas em client-semantic-context.ts (collectMetricIds, linhas 57-67,124) — que monta o contexto semântico/IA das métricas surfaçadas. No caminho de execução de dados (execute-metric.ts) o gating é por ownerClientId + rota + acesso a dataset + cobertura; não há referência a enabledIndicators ali. Ou seja, restringir enabledIndicators não impede, por si só, a execução de uma métrica via API se as demais checagens passarem. Vila Rosa usa enabledIndicators: null (todas), então o ponto é latente, não ativo hoje (seed-vila-rosa-client.mjs:227,241).

  9. Divergência productId × contractRef documentada no próprio seed. Existem produtos legados credit/covenants no Firestore (domínio de emissão/dívida, 8 clientes), sem relação com o domínio imobiliário do Vila Rosa (seed-vila-rosa-client.mjs:17-46). A resolução de métricas usa contractRef = prefixo de requires[0], não productId (execute-metric.ts:210). Isso torna a nomenclatura sensível: o productId do binding e o contractRef precisam ser escolhidos com cuidado (aqui, ambos iguais: liquid-play/liquid-play-plus), senão as métricas falham 422 silenciosamente para o usuário. É uma armadilha de configuração, não um bug — mas exige conhecimento não óbvio para onboardar um cliente novo.

  10. Perfil criado no login nasce sem permissão. fetchProfile cria users/{uid} com groups: [] e clientAccess: [] quando o usuário loga sem doc prévio (useAuth.ts:65-77). Sem intervenção de admin, esse usuário vê "Nenhum cliente disponível"/"Sem permissão" (ProtectedRoute.tsx:69-90). Correto do ponto de vista de segurança (fail-closed), mas significa que o onboarding de usuário é obrigatoriamente manual (UI admin ou seed).

#Bases de dados e contratos de dados

Esta seção documenta a camada de dados do liquid-dataviz: como o produto se conecta ao BigQuery, como o vocabulário de dados é declarado em Data Contracts no Firestore, como métricas são resolvidas em SQL executável contra o dataset de cada cliente, e quais rotas de API servem dados às páginas. Todas as afirmações têm referência de arquivo (caminho:linha). Foi analisado o código real; onde o CLAUDE.md ou uma ADR divergem do código, isso está registrado na seção final.

Há duas fontes de armazenamento com papéis distintos (CLAUDE.md; ADR-0013): o Firestore guarda configuração e metadados — dataSources, dataContracts (+ entities/attributes), metrics, relations, products, clients (com productBindings), dashboardTemplates, groups, users e os reports por cliente; o BigQuery guarda exclusivamente os dados de negócio de cada cliente (carteira/contratos/pagamentos/covenants). O banco Firestore canônico é liquid-play-dataviz (src/shared/lib/runtime-config.ts:2-4,28-30).

O modelo semântico (ADR-0015) tem cinco níveis: Data Source (físico) → Data Contract + Metric Catalog (semântico) → Product (empacotamento) → Client (tenant, com schemaBindings por dataset). A execução de uma métrica é a cadeia Template → metricId → Metric.recipe → ClientDatasetBinding → DataSource → BigQuery (app/api/metrics/[id]/data/route.ts:20-23). O caminho legado /api/bigquery + fetchBigQuery descrito no CLAUDE.md não existe mais (removido no PR #42 — ver Observações e docs/mapeamento-restos-codigo-pos-data-driven.md:16,162-166).

#Integração BigQuery

#Cliente e credenciais

src/shared/lib/bigquery/client.ts é a fábrica de clientes BigQuery, com cache in-memory por processo (clients: Map, client.ts:16-17).

  • getBigQueryClient() (sync, sem args) — cliente default montado a partir de env vars (client.ts:49-55). buildDefaultOpts() lê BIGQUERY_PROJECT_ID (fallback GOOGLE_CLOUD_PROJECT), BIGQUERY_LOCATION/GOOGLE_CLOUD_LOCATION e BIGQUERY_CREDENTIALS como keyFilename (client.ts:35-44). Mantido para retrocompat — hoje só o queryFilterOptions o usa.
  • getBigQueryClientFor(dataSourceId) (async) — resolve o DataSource no Firestore e monta um cliente com projectId/location daquele documento (client.ts:61-80). É o caminho usado pela pipeline semântica de métricas.

Escopos OAuth solicitados quando se usa service-account key: bigquery e drive.readonly (client.ts:30-33). O drive.readonly é necessário para ler external tables apontando para Google Sheets/Drive; sem ele o GCP retorna "Permission denied while getting Drive credentials" mesmo com a planilha compartilhada (client.ts:19-28). Sob ADC (usuário humano), os escopos vêm do gcloud auth application-default login e essa lista é ignorada.

Constantes de retrocompat: DEFAULT_DATASET (env BIGQUERY_DATASET, default liquid_dataviz, client.ts:83) e TABLES (contratos/pagamentos/fluxo_caixa hard-coded, client.ts:86-90).

#Fluxo de dados completo (estado atual)

O CLAUDE.md descreve hook → fetchBigQuery(action) → POST /api/bigquery; isso é legado. O fluxo real é:

  1. Uma página (dashboard)/*/page.tsx renderiza <RouteTemplatePage templateId=…/> (fino wrapper — docs/mapeamento-restos-codigo-pos-data-driven.md:36-39).
  2. O template (Firestore dashboardTemplates ou reports) traz um blockMap; cada bloco pode ter metricId/sparklineMetricId.
  3. useReportData(blockMap, …) coleta os metricId dos blocos (useReportData.ts:252-267), monta uma cacheKey com dataset/cliente/filtros (useReportData.ts:269-285) e chama fetchMetricsBatch.
  4. fetchMetricsBatch obtém o token (external-token ou Firebase idToken) e faz POST /api/metrics/batch com {clientId, productId, metricIds, pageFilters, ambientFilters} (useReportData.ts:59-101).
  5. O backend resolve cada métrica (ver Rotas API de dados) e devolve linhas. Falha por-métrica não derruba a página: vira rows vazias + console.error (useReportData.ts:92-99).
  6. applyMetricRowsToBlock mapeia as linhas para o shape de cada tipo de bloco (kpi/chart/table/donut/gauge) por convenção de colunas bucket/value (useReportData.ts:103-190).

Convenções de saída do resolver consumidas pelo front: coluna bucket → eixo X; coluna value → série principal/valor do KPI; percentuais vêm como razão 0–1 e o ×100 acontece na fronteira de apresentação (useReportData.ts:41-44,128-131). Não há React Query/SWR; o cache é a cacheKey + fetchedRef do próprio hook (useReportData.ts:393-397) — o "cache de 5 min" do CLAUDE.md refere-se ao useQuery custom legado, não a esta pipeline.

#Data Contracts (camada semântica)

Um Data Contract é o vocabulário canônico de entities (tabelas lógicas) e attributes (campos lógicos) que os Products consomem, desacoplado do Product (ADR-0015; src/shared/schemas/data-contract.ts:5-20). Hierarquia Firestore (data-contract.ts:12-19):

dataContracts/{contractId}                                          (doc)
  entities/{entityId}                                               (subcol)
    attributes/{attributeId}                                        (subcol)

#Schemas

DataContractDoc (data-contract.ts:29-36): name, version (semver x.y.z), status (draft|active|deprecated, data-contract.ts:27), description, timestamps.

EntityDoc (data-contract.ts:42-47): label, description, timestamps. id é SqlIdentifier.

AttributeDoc (data-contract.ts:53-71):

Campo Tipo/Regra Nota
entityId SqlIdentifier denormalizado (duplica o pai)
label string 1–80
description string ≤500
type FieldType enum STRING/INT64/NUMERIC/BIGNUMERIC/FLOAT64/BOOL/DATE/DATETIME/TIMESTAMP/TIME/BYTES/GEOGRAPHY/JSON (product.ts:17-30)
unit string ≤20 livre: BRL, %, dias, m²
isKey / required bool
deprecated / deprecatedReason bool / string imutabilidade light: nunca deletar, só depreciar (data-contract.ts:63-68)

Single vs Multi-Contract: o ADR-0015 previu um único contract canonical no MVP (data-contract.ts:18-19; ADR-0015:117-127), mas na prática já existem múltiplos contracts nomeados — liquid-play, liquid-play-plus (seed-liquid-play-contracts.mjs:3-6), além do legado canonical e do produto covenants/credit de emissão de dívida (seed-vila-rosa-client.mjs:20-25). #Detecção automática de schema (/api/schema-detect/v2)

#Cobertura do contrato pelo cliente

Para uma métrica executar, o cliente precisa cobrir os atributos de requires no contract correspondente. A pré-checagem collectBindingGaps (src/shared/lib/metrics/coverage.ts:21-40):

  • Cliente legado (schemaBindings vazio) → sem lacunas (fallback back-compat, coverage.ts:26-28).
  • Cliente migrado: para cada ref 3-part do contract, se o mapping entity.attr está ausente → sem-mapping; se está null → desabilitado (coverage.ts:31-38).

Quando há lacunas, executeMetric falha com 422 e a mensagem Cliente não cobre todos os atributos exigidos pela métrica no contrato "X", anexando o array missing de CoverageGap (src/shared/lib/metrics/execute-metric.ts:240-244). Importante: essa pré-checagem só roda para recipes que não são sql (execute-metric.ts:240); recipes sql pulam a cobertura e só falham fail-loud no resolveColumn (ver abaixo).

#Refs de catálogo (Product / Template / Report) — soft + warning

Diferente de requires (dados), as refs de catálogo entre documentos de config não têm FK rígida e degradam graciosamente (app/api/products/route.ts:25-33):

#Resolução: resolveColumn e o binding do cliente

Existem duas funções resolveColumn com semânticas diferentes.

#1. Resolver semântico (resolve-metric.ts) — fail-loud

src/shared/lib/metrics/resolve-metric.ts:71-107 resolve entity.attribute → coluna real via binding.schemaBindings (ADR-0015 §Resolution rules):

  • mapeado para string → usa a coluna (quoted) (:83-85);
  • mapeado para null → MetricResolutionError (cliente declarou indisponível) (:76-82);
  • ausente + cliente migrado (schemaBindings não-vazio) → MetricResolutionError (assumir o attributeId arriscaria consultar coluna inexistente) (:91-100);
  • ausente + cliente legado (schemaBindings vazio) → fallback: usa o próprio attributeId como coluna, emitindo console.warn (:101-107).

Variante tryResolveColumn (:114-122) retorna null em vez de lançar — usada por filtros ambiente (best-effort, pulam quando a coluna não existe).

tableRef (:130-144) resolve a tabela física aplicando tableBindings (entityId → tableId divergente) quando presente, com fallback entityId.

#2. Resolver legado (schema-resolver.ts) — soft

src/shared/lib/bigquery/schema-resolver.ts:22-34 opera sobre o ClientSchema nested (tabela → campo → coluna|null):

  • sem schema / sem mapping → retorna o próprio nome do campo (back-compat, :27-32);
  • mapeado para null → retorna null (indisponível, :32).

resolveColumnOrThrow (:62-70) é a única parte fail-loud deste módulo: lança FieldUnavailableError quando o campo está mapeado para null (:51-56). É o contrato testado que sobreviveu ao cleanup (docs/mapeamento-restos-codigo-pos-data-driven.md:130-134).

#Como uma métrica vira SQL

resolveMetric (resolve-metric.ts:635-653) despacha por kind:

  • aggregation (resolveAggregationRecipe, :301-378): monta SELECT com DATE_TRUNC para série, colunas de group-by, aggExpr para o valor (sempre AS value), FROM tableRef, WHERE de filters + ambientFilters, GROUP BY, ORDER BY, LIMIT.
  • sql (resolveSqlRecipe, :380-446): substitui, na ordem, {filter.X} / {filter.X:entity.attr} (:394-421), {ambient:entity} (:424-434), {entity.attr} → coluna (:436-439) e {entity} → tabela (:441-443).
  • derived (resolveDerivedMetric, :513-633): resolve bindingsByContract, monta FROM + JOINs por relations (só col(leftRef) = col(rightRef), sem qualificar tabela, :546-564), agrega terms e renderiza a expression validada (:566-573). Fail-loud se contrato sem binding, relação ausente ou relação que não conecta as entidades em escopo (:520-529,547-560).

Filtros de página (PageFilterValue) têm 3 kinds: date_range (BETWEEN), snapshot (=) e in (IN UNNEST) (resolve-metric.ts:35-38); quando o filtro não está preenchido, vira no-op 1=1/TRUE (:172-175,189,433).

#Camada semântica: métricas e indicadores

#Visão geral

A camada de métricas é o coração analítico do liquid-dataviz. Uma métrica (também chamada de indicador) é um documento canônico armazenado na coleção Firestore metrics, com id no formato domain.slug (ex.: pdd.total, covenants.indice_recebivel). Cada métrica declara o que calcular em um vocabulário abstrato de entidade.atributo — nunca colunas físicas — e de que dados depende via requires[] (refs 3-partes contrato.entidade.atributo). A métrica é agnóstica de cliente: a mesma definição serve todos os tenants; o que varia é o binding de cada cliente, que traduz entidade.atributo para a coluna física real da tabela BigQuery daquele cliente (src/shared/schemas/metric.ts:1-224, ADR-0015).

O fluxo canônico é: Bloco de canvas (metricId) → Metric.recipe → ClientDatasetBinding do cliente → DataSource (projeto GCP) → SQL BigQuery → linhas → formatação no front. O front dispara tudo por useReportData, que faz um POST em lote a /api/metrics/batch; o back-end lê a métrica, escolhe o binding do cliente, resolve o recipe em SQL parametrizado (resolveMetric/resolveDerivedMetric), executa no BigQuery e devolve as linhas. A resolução tem duas garantias de segurança: identificadores SQL sempre sanitizados por helpers safe*/quote* (src/shared/lib/bigquery/identifier.ts) e valores sempre em parâmetros nomeados (@nome), nunca interpolados (src/shared/lib/metrics/resolve-metric.ts:18-22).

Existem três tipos de "receita" (recipe): aggregation (agregação declarativa GROUP BY/DATE_TRUNC), sql (template SQL literal com tokens de placeholder) e derived (junção cross-entity/cross-contract via relations + expressão aritmética). O catálogo covenants.* v2 do cliente Vila Rosa (scripts/metrics/covenants-v2.mjs, 64 métricas) usa exclusivamente aggregation e sql; o catálogo play.* (dashboard base) usa os três. Uma métrica sem recipe é apenas um rótulo semântico (caminho legado), não executável (metric.ts:190-195, execute-metric.ts:142-144).

#Recipe aggregation (AggregationRecipe, metric.ts:97-117)

Campo Tipo Papel
kind 'aggregation' discriminante
primaryEntity EntityRef vira FROM <tabela-bound>
aggregation sum | count | count_distinct | avg | min | max função agregada (metric.ts:58-65)
valueAttribute entidade.atributo? coluna agregada; opcional para count/count_distinct

Exemplo real (play-elegibilidade.mjs:86-93):

agg({
  id: 'play.ltv_distribuicao_saldo', type: 'chart', unit: 'BRL',
  primaryEntity: 'contratos', aggregation: 'sum',
  valueAttribute: 'contratos.saldo_devedor',
  groupByAttributes: ['contratos.faixa_ltv'],
  filters: [{ attribute: 'contratos.data_base_report', op: '=', value: 'filter.snapshot' }],
  requires: ['liquid-play.contratos.saldo_devedor', 'liquid-play.contratos.faixa_ltv', 'liquid-play.contratos.data_base_report'],
})

#Recipe sql (SqlRecipe, metric.ts:119-128)

Um único campo: template (string 1–10000). O nome do campo é template, não sql (covenants-v2.mjs:11-13). O template usa tokens de placeholder resolvidos pelo resolveSqlRecipe (ver seção de Resolução). Exemplo real de KPI com snapshot-pin (covenants-v2.mjs:308-319):

SELECT SAFE_DIVIDE(SUM({contratos.valor_atraso}), SUM({contratos.saldo_devedor})) AS value
FROM {contratos}
WHERE {contratos.data_base_report} = (
  SELECT MAX({contratos.data_base_report}) FROM {contratos}
)

#Recipe derived (DerivedRecipe, metric.ts:136-167)

Junta entidades (possivelmente de contratos diferentes) via relations e combina termos agregados numa expression aritmética validada.

Campo Tipo Papel
kind 'derived' discriminante
primaryEntity ContractEntityRef (2-partes contrato.entidade) FROM
joins [{relationId}] resolve relações por id (relations/{id})
terms DerivedTerm[] min 1 {id, aggregation, valueRef?} — id local usado na expression
expression string 1–500 aritmética só com ids de termos, números e + - * / ( )
timeRef / timeGrain AttributeRef? / grain série
groupByRefs AttributeRef[] agrupamentos 3-partes
filters DerivedFilter[] (attribute 3-partes) filtros
orderBy / limit

Exemplo real — LTV médio ponderado (play-elegibilidade.mjs:75-81):

derived({
  id: 'play.ltv_medio', unit: '%', primaryEntity: 'liquid-play.contratos',
  terms: [
    { id: 'sd', aggregation: 'sum', valueRef: 'liquid-play.contratos.saldo_devedor' },
    { id: 'vi', aggregation: 'sum', valueRef: 'liquid-play.contratos.valor_imovel' },
  ],
  expression: 'sd / vi',
  filters: [{ attribute: 'liquid-play.contratos.data_base_report', op: '=', value: 'filter.snapshot' }],
  requires: [/* ... */],
})

A expression passa por um parser/validador anti-injeção (src/shared/lib/metrics/expression.ts): tokeniza só identificadores, números e + - * / ( ); recusa ., ; e qualquer token fora da gramática; exige que todo identificador seja um id de termo declarado; valida balanceamento de parênteses (expression.ts:31-51). Depois renderExpression substitui cada id pelo SQL agregado do termo (expression.ts:53-56).

#Enum de operadores de filtro (FilterOp, metric.ts:69-81)

= != < <= > >= in not_in between is_null is_not_null. O value de um filtro (FilterValue, metric.ts:83-89) pode ser literal, array de literais ou uma referência de filtro de página no formato filter.<key> (regex ^filter\.[a-z_][a-z0-9_]*$).

#Resolução: como uma métrica vira SQL

Fonte: src/shared/lib/metrics/resolve-metric.ts. O ponto de entrada é resolveMetric() (resolve-metric.ts:635-653) para recipes aggregation/sql, e resolveDerivedMetric() (resolve-metric.ts:513-633) para derived (chamado separadamente porque é multi-binding). O retorno é sempre { sql, params, outputColumns } (resolve-metric.ts:40-45).

#Resolução de coluna (resolveColumn, resolve-metric.ts:71-107)

Regra central da tradução entidade.atributo → coluna física, contra binding.schemaBindings (ADR-0015 §Resolution rules):

  1. schemaBindings[ref] é string → usa essa coluna (quotada em backticks).
  2. schemaBindings[ref] é null → falha-cedo com MetricResolutionError ("Attribute ... marcado como indisponível") — cliente declarou o atributo indisponível (resolve-metric.ts:77-82).
  3. binding ausente para a key e cliente migrado (schemaBindings não-vazio) → falha-cedo ("sem mapping em schemaBindings") — evita consultar coluna inexistente (resolve-metric.ts:94-100).
  4. binding ausente e cliente legado (schemaBindings vazio) → fallback back-compat: usa attributeId como nome da coluna, com console.warn (resolve-metric.ts:101-106).

tryResolveColumn (resolve-metric.ts:114-122) é a variante soft usada por filtros ambiente: retorna null em vez de lançar quando o atributo está indisponível (semântica best-effort). Isso alinha com a regra do projeto: apenas o caminho de dados (resolveColumn) é fail-loud; refs de catálogo e filtros ambiente são soft+warning.

tableRef (resolve-metric.ts:130-144) resolve a tabela física da entidade, aplicando tableBindings (entityId → tableId divergente) quando presente; default 1:1 (entityId == tableId). É exportada para reúso fora do pipeline (ex.: /api/metrics/filter-values).

#Recipe aggregation → SQL (resolveAggregationRecipe, resolve-metric.ts:301-378)

Fluxo:

  1. Se timeAttribute: adiciona DATE_TRUNC(<col>, <grain>) AS bucket como primeira coluna e ao GROUP BY (resolve-metric.ts:315-323).
  2. Cada groupByAttributes[i] vira <col> AS <alias> (alias = parte atributo da ref) e entra no GROUP BY (resolve-metric.ts:326-332).
  3. Coluna agregada sempre chamada value: <agg>(<valueAttribute|*>) AS value; sum/avg/min/max sem valueAttribute → erro (resolve-metric.ts:334-345).
  4. FROM via tableRef(primaryEntity); WHERE = filtros da recipe (buildFilterClause) + filtros ambiente aplicáveis (buildAmbientClause) (resolve-metric.ts:347-356).
  5. ORDER BY: orderBy explícito, ou bucket ASC se série; LIMIT opcional (resolve-metric.ts:358-364).

Formato de saída: LONG. Uma recipe aggregation com groupByAttributes produz uma linha por bucket × categoria (colunas bucket, <dimensão>, value) — nunca pivota para uma coluna por série (ver Observações).

#Recipe sql → SQL (resolveSqlRecipe, resolve-metric.ts:380-446)

Substituições no template, nesta ordem (a ordem importa):

  1. {filter.<key>} e {filter.<key>:<entidade.atributo>} — substituído ANTES dos demais para a regex de entidade.atributo não capturar filter.date_range por engano (resolve-metric.ts:394-421). Comportamento por kind do page filter:
    • ausente (page filter não preenchido) → 1=1 (no-op; a métrica continua executando) — confirmado em resolve-metric.ts:397-398.
    • date_range → <col> BETWEEN @start AND @end.
    • snapshot → <col> = @valor.
    • in com valores → <col> IN UNNEST(@nome); in vazio → 1=1. O sufixo :entidade.atributo permite sobrescrever qual coluna o filtro usa quando a entidade do template não é a default do filtro de página (resolve-metric.ts:392-399).
  2. {ambient:<entidade>} — substituído pelas cláusulas dos filtros ambiente daquela entidade (ANDed), ou TRUE (no-op) se nenhuma (resolve-metric.ts:422-434).
  3. {entidade.atributo} → coluna real via resolveColumn (resolve-metric.ts:435-439).
  4. {entidade} → tabela qualificada via tableRef (resolve-metric.ts:440-443).

outputColumns retorna vazio ([]) para recipes sql (resolve-metric.ts:445) — o front infere o shape pelas chaves das linhas.

Helpers do catálogo Vila Rosa que geram templates padronizados (covenants-v2.mjs:111-125): snapshotKpi(entity, expr) monta o KPI snapshot-pin de coluna única; pinClause(entity) gera a cláusula de pin para SELECTs multi-coluna.

#Pattern snapshot-pin

Convenção do projeto (introduzida pelo patch one-off scripts/patch-covenants-snapshot-pin.mjs, já removido): fixar a consulta no snapshot mais recente da tabela via subquery — WHERE {entidade.data_base_report} = (SELECT MAX({entidade.data_base_report}) FROM {entidade}) (covenants-v2.mjs:49-54, 111-125). Só é expressável em kind:'sql' (a aggregation não suporta subquery). Distingue-se do filtro de página {filter.snapshot}/{filter.date_range} — ver Observações (o pin ignora a seleção do usuário; o filtro de página respeita).

#Formato WIDE (pivot) para gráficos empilhados

Gráficos de séries empilhadas (stacked-bar) exigem uma coluna por série por bucket — formato WIDE. Como aggregation só emite LONG, essas métricas são escritas em kind:'sql' com pivot manual via CASE/IF. Dois padrões reais:

  • SUM(IF(<dim> = 'X', <valor>, 0)) AS <serie> por bucket (covenants-v2.mjs:414-424 — faixa_atraso2_valor_serie).
  • COUNT(DISTINCT IF(<dim> = 'X', id, NULL)) AS <serie> por bucket (covenants-v2.mjs:392-402 — faixa_atraso2_contratos_serie; covenants-v2.mjs:457-471 — rating_serie).
  • SUM(CASE WHEN <dim> ... THEN <valor> ELSE 0 END) AS <serie> (play-elegibilidade.mjs:150-172).

Os aliases snake_case dessas colunas (sem_atraso, f1a30, a–h, etc.) são load-bearing: devem casar com os dataKeys dos templates de report que consomem a métrica (covenants-v2.mjs:379-383).

#Recipe derived → SQL (resolveDerivedMetric, resolve-metric.ts:513-633)

Multi-binding: cada contractId tem seu próprio ClientDatasetBinding (bindingsByContract). Refs são 3-partes contrato.entidade.atributo.

  1. col(ref) resolve coluna via binding do contrato daquela ref; table(ceRef) resolve a tabela (resolve-metric.ts:530-539).
  2. FROM = primaryEntity; para cada join, encontra a Relation por id, checa que ela conecta exatamente uma entidade já no escopo a uma nova, e adiciona JOIN <tabela> ON <col(leftRef)> = <col(rightRef)> (resolve-metric.ts:541-564). Fail-loud: relação ausente ou que não conecta o escopo → MetricResolutionError (resolve-metric.ts:549-560).
  3. Termos viram agg(col); validateExpression + renderExpression compõem o value final (resolve-metric.ts:566-573).
  4. timeRef/groupByRefs/filters/orderBy/limit análogos aos outros recipes (resolve-metric.ts:575-618).

#Execução, gating e multi-tenancy

Fonte: src/shared/lib/metrics/execute-metric.ts, consumido por /api/metrics/[id]/data (uma métrica) e /api/metrics/batch (até 50 por request). O executeMetric (execute-metric.ts:118-259) nunca lança por erro de negócio — cobertura, tenant, propriedade e resolução viram ok:false; erro inesperado de BQ/Firestore vira ok:false 500 com mensagem genérica (execute-metric.ts:20-27, 254-258).

#Sequência de checagens (single-contract)

  1. Propriedade: ownerClientId != null && != clientId → 403 "Métrica pertence a outro cliente". Global (null) é visível a todos (execute-metric.ts:137-141).
  2. Recipe presente: sem recipe → 422 não-executável (execute-metric.ts:142-144).
  3. Permissão de rota (G1): routeForMetric(metric.id) → se a métrica serve uma página específica, exige verifyRouteAccess (paridade com /api/bigquery). Métricas compartilhadas (null) ficam só com o tenant-check (execute-metric.ts:147-154).
  4. Seleção de dataset por contrato: metricContractId = requires[0].split('.')[0]. Procura entre os productBindings do cliente um dataset cujo contractRef bate com esse contrato. Nenhum cobre → 422 "Nenhum dataset do cliente cobre o contrato ..." (execute-metric.ts:209-225).
  5. Papel do productId: só ordena a preferência de bindings — coloca os bindings do produto informado na frente, mas a seleção final é por contractRef (execute-metric.ts:216-223). Fallback: sem contrato, pega binding do produto ou o primeiro; dataset isPrimary ou o primeiro (execute-metric.ts:227-232).
  6. Tenant-check do dataset: verifyDatasetAccess(email, datasetId, clientId) → não permitido → 403 (execute-metric.ts:234-235).
  7. Cobertura de atributos: para recipes não-sql (aggregation), collectBindingGaps(requires, dataset, contractId) — se houver lacunas → 422 "Cliente não cobre todos os atributos exigidos pela métrica no contrato ..." com a lista missing[] (execute-metric.ts:240-245).
  8. Resolução + execução: resolveMetric(...) gera SQL+params; executa via getBigQueryClientFor(dataSourceId) (execute-metric.ts:247-253).

Cobertura (src/shared/lib/metrics/coverage.ts:21-40): cliente legado (schemaBindings vazio) ⇒ sem lacunas (fallback); migrado com ref ausente ⇒ sem-mapping; ref mapeada a null ⇒ desabilitado. Refs de outros contratos são ignoradas.

#Caminho derived (cross-contract, execute-metric.ts:156-207)

  1. Coleta todos os contractId referenciados (primaryEntity, terms, groupByRefs, filters, timeRef e ambos os lados de cada relation dos joins) (execute-metric.ts:158-170).
  2. Para cada contrato, acha um dataset com contractRef igual; ausente → 422 "Cliente não cobre o contrato ... exigido pela métrica". Tenant-check por dataset (execute-metric.ts:177-197).
  3. Todos os contratos devem estar no mesmo projeto BigQuery — projetos distintos → 422 "Métrica cross-contract exige datasets no mesmo projeto" (execute-metric.ts:199-201).
  4. resolveDerivedMetric(...) + query BQ (execute-metric.ts:203-206).

#Batch e degradação

/api/metrics/batch carrega bindings e métricas uma vez, lê relations só se alguma métrica é derived, e faz fan-out das queries em paralelo com caches de DataSource/access-check (batch/route.ts:55-107). Falha por-métrica não derruba o batch (HTTP 200 com results[id].ok=false). No front, fetchMetricsBatch transforma falha por-métrica em linhas vazias + console.error — a página não quebra, mas a falha fica silenciosa na UI (useReportData.ts:90-100).

#metric-route-map (src/shared/lib/permissions/metric-route-map.ts)

Mapa metricId → rota para enforcement server-side de canAccessRoute no path semântico (metric-route-map.ts:1-13). routeForMetric(id) retorna a rota ou null (metric-route-map.ts:157-159). Registrar uma métrica nova que sirva uma página específica = adicionar a entrada no objeto METRIC_ROUTE. Métricas de carteira básica compartilhada entre /dashboard e /elegibilidade (play.total_contratos, saldo_*, séries, inadimplencia*, etc.) são deliberadamente omitidas (retornam null → só tenant-check), porque uma única rota não as descreve (metric-route-map.ts:5-13). Todas as 64 métricas covenants.* mapeiam para /g (reports dinâmicos em app/(dashboard)/g/[groupId]/r/[reportId]), pois servem templates de report, não uma página fixa (metric-route-map.ts:74-155).

#Gating por cliente (enabledIndicators)

ClientProductBinding.enabledIndicators (client-binding.ts:73-78) é a "lista de métricas liberadas" por produto contratado. Quando não-null, funciona como interseção: só os ids listados são surfaçados; null/ausente ⇒ todas as métricas do produto (client-semantic-context.ts:57-67, 124). Ver Observação sobre onde esse gating é (e não é) aplicado.

#Filtros

#Filtros de página (page filters)

Compostos no front por useReportData a partir dos defaults do template (CanvasPageFilters.metricPageFilters) ou de um hardcode sensato em contratos (useReportData.ts:220-223, 307-328). Tipos (PageFilterValue, resolve-metric.ts:35-38): date_range ({start, end, attribute}), snapshot ({value, attribute}), in ({values, attribute}). O front deriva:

  • date_range a partir do dateRange global (com fallback de 365 dias) (useReportData.ts:297-313).
  • snapshot = fim do período (useReportData.ts:314-315).
  • in com control:'dropdown' = seleção local do usuário na página; senão = projetos global. Vazio ⇒ no-op 1=1 (useReportData.ts:316-327).

O back-end valida esses filtros por Zod na borda das rotas (batch/route.ts:27-31, [id]/data/route.ts:29-46).

#Filtros ambiente (advanced filters)

AmbientFilter (src/shared/lib/metrics/ambient-filter.ts:17-28): op:'in' (coluna IN (valores)) ou op:'numeric_buckets' (OR de buckets numéricos). São best-effort: aplicados só quando o attribute (entidade.atributo) bate com o primaryEntity da métrica e a coluna está bound; caso contrário, pulados (resolve-metric.ts:270-281, 422-434, 601-611). advancedFiltersToAmbient (dashboard-ambient.ts:28-48) mapeia os filtros avançados da UI (ratings, elegibilidade, faixaLtv, faixaAtraso, tipoProponente, gruposRepasse) + o projeto selecionado para AmbientFilter[], parametrizando o prefixo de entidade por página (dashboard-ambient.ts:19-26).

#Formatação (renderização dos valores)

Fonte: formatValue em src/shared/hooks/useReportData.ts:28-51 + src/shared/lib/format.ts. O front converte o valor cru do BigQuery para string exibível segundo o format do bloco de canvas (não da métrica):

  • currency → formatCurrency(value) — ignora decimals (a função tem regra própria de casas e abrevia em mi/mil); R$ X,XX mi ≥ 1M, R$ X,XX mil ≥ 1k (useReportData.ts:36-39, format.ts:3-21).
  • percent → formatPercent(value * 100, decimals) — o catálogo emite razão 0–1 e o ×100 acontece na fronteira de apresentação (useReportData.ts:41-43, format.ts:23-29).
  • number → formatNumber(value, decimals) — para valores 0–100 crus (com decimals/suffix) (useReportData.ts:44-46, format.ts:31-37).
  • default → String(value) (useReportData.ts:47-48).
  • suffix é concatenado ao final quando presente (useReportData.ts:50).

O adapter por tipo de bloco (applyMetricRowsToBlock, useReportData.ts:103-190) usa as convenções do resolver:

  • kpi: primeira linha, coluna value (ou primeira chave); formata com format/decimals/suffix do bloco (useReportData.ts:107-119).
  • chart: bucket → xAxisKey; value → primeiro dataKey; demais colunas passam direto (WIDE) (useReportData.ts:120-145).
  • table: linhas cruas (useReportData.ts:146-159).
  • donut: value = valor do slice; nome do slice = primeira coluna que não seja value/bucket (useReportData.ts:160-181).
  • gauge: valor numérico da primeira linha (useReportData.ts:182-189).
  • sparkline: série de value por bucket; calcula trend a partir dos dois últimos pontos (useReportData.ts:192-218).

#Observações e possíveis inconsistências

Fatos com referência de arquivo (sem especulação):

  1. metric.unit não dirige a formatação. unit ('%', 'BRL', 'm²', 'BRL/m²') é persistido só por back-compat e a unit canônica "vive no Attribute" (metric.ts:186-187). Quem formata é o format do bloco de canvas (useReportData.ts:107-118). Uma métrica unit:'BRL/m²' só será exibida como moeda/número/percentual conforme o bloco decidir — divergência entre a unit declarada e o format do bloco fica silenciosa.

  2. A convenção percent (razão 0–1) depende do bloco declarar format:'percent'. O ×100 só ocorre nesse ramo (useReportData.ts:41-43). Se o bloco que consome uma métrica de razão 0–1 declarar format:'number', o valor 0.0066 renderiza como "0" (decimals default 0), não 0,66%. É um acoplamento implícito catálogo↔bloco, sem validação que o garanta.

  3. Coverage pré-check é pulado para recipes sql. collectBindingGaps só roda quando metric.recipe.kind !== 'sql' (execute-metric.ts:240). Métricas sql (a maioria de covenants.*) não recebem o erro agregado "Cliente não cobre todos os atributos ..." com lista missing[]; em vez disso falham coluna-a-coluna dentro de resolveColumn (resolve-metric.ts:77-100), virando 422 genérico da MetricResolutionError (execute-metric.ts:255).

  4. resolveDerivedMetric monta o JOIN sem qualificar alias de tabela. O JOIN é JOIN <tabela> ON <col(leftRef)> = <col(rightRef)> (resolve-metric.ts:562), e col() produz a coluna quotada sem prefixo de tabela. Para entidades com colunas homônimas (comuns neste domínio: id_contrato, data_base_report, empresa, projeto, status_contrato), o BigQuery retorna Column name ... is ambiguous. Confirmado empiricamente e documentado no header do catálogo (covenants-v2.mjs:20-47): por isso os três joins do Vila Rosa foram feitos em kind:'sql' com aliases manuais (fc./ c.), não em derived. Efeito: derived é inutilizável para joins entre entidades com colunas de mesmo nome.

  5. Recipes aggregation com groupByAttributes só produzem formato LONG. resolveAggregationRecipe não pivota (resolve-metric.ts:326-332) — uma linha por bucket × categoria. Isso é incompatível com stacked-bar (que precisa de uma coluna por série). Vários metrics do Vila Rosa que eram aggregation + groupBy tiveram de ser reescritos como sql com pivot manual (covenants-v2.mjs:369-385, 532-536, 609-611).

  6. Snapshot-pin (subquery MAX) ignora o filtro de snapshot/período da página. KPIs covenants.* construídos com snapshotKpi/pinClause pinam sempre o último data_base_report da tabela inteira (covenants-v2.mjs:111-125, resolve-metric.ts sem interpolar page filter na subquery). Já o catálogo play.* usa {filter.snapshot}, que respeita a data base selecionada pelo usuário (play-elegibilidade.mjs:20, 67). Ou seja: dois catálogos com semânticas diferentes de "snapshot" — os KPIs Vila Rosa não reagem ao seletor de período; os do dashboard base reagem.

  7. Recipes sql só respeitam filtros de página/ambiente se o autor incluir os tokens. Ao contrário de aggregation (que aplica filtros ambiente automaticamente ao WHERE, resolve-metric.ts:353-356), num sql os filtros só entram onde houver {filter.X}/{ambient:entidade} no template. Omitir o token faz a métrica ignorar o filtro silenciosamente — não há validação. Isso é usado intencionalmente em algumas séries "all-time" do Vila Rosa (covenants-v2.mjs:1142-1150, 384), mas o mesmo mecanismo mascara omissões acidentais.

  8. enabledIndicators não é aplicado no caminho de execução. O gating por lista liberada só é consumido por getClientSemanticContext (client-semantic-context.ts:57-67, 124), que monta contexto para reúso da IA. executeMetric não checa enabledIndicators (execute-metric.ts:118-253): passadas as barreiras de propriedade, rota, tenant e cobertura, uma métrica fora da lista liberada ainda é executável via /api/metrics/[id]/data ou /batch.

  9. Seleção de dataset depende da ordem de requires. metricContractId vem de requires[0] (execute-metric.ts:210). Se requires[0] apontar para um contrato diferente do principal do template, o dataset escolhido pode divergir do esperado. Para recipes sql isso é mais sensível porque todas as {entidade.atributo} são resolvidas contra esse único binding (resolveSqlRecipe), i.e. um sql é intrinsecamente single-contract — um template que misture entidades de dois Data Contracts não resolve corretamente (o resolver não seleciona um segundo binding). Joins genuinamente cross-contract exigem derived (que, por sua vez, tem a limitação nº 4).

  10. DerivedFilter não expressa snapshot-pin, igualdade extra de join nem CAST. Aceita só attribute op literal/page-filter (resolve-metric.ts:452-490, metric.ts:136-141). Não há hook para subquery MAX(data_base_report), para a igualdade adicional em data_base_report que algumas relations exigem, nem para CAST(...) no ON do JOIN — motivos adicionais (além do nº 4) pelos quais o Vila Rosa evitou derived (covenants-v2.mjs:29-47).

  11. outputColumns vazio para sql. resolveSqlRecipe retorna outputColumns: [] (resolve-metric.ts:445); o front infere o shape pelas chaves das linhas. Consequência: o nome do alias no template é load-bearing para blocos que dependem de convenção — donut usa a primeira coluna ≠ value/bucket como nome do slice (useReportData.ts:169-177) e o waterfall lê r.bucket literal (por isso extrato_resumido teve de aliasar a categoria AS bucket, covenants-v2.mjs:1223-1233).

  12. Erros de execução são mascarados por design. Erro inesperado de BQ/Firestore vira 500 genérico "Erro ao executar métrica" para não vazar SQL/topologia (execute-metric.ts:256-257); no batch, cada falha vira rows vazias + console.error no cliente (useReportData.ts:95-98). Bom para segurança, mas dificulta diagnóstico: a página renderiza vazia sem sinal visível de erro.

  13. Fallback de cliente legado assume nome de coluna = attributeId. Quando schemaBindings está vazio, resolveColumn usa attributeId como coluna real, apenas com console.warn (resolve-metric.ts:101-106). Se um cliente legado não tiver a coluna exatamente com esse nome, a query falha em runtime no BQ (ou, pior, atinge coluna homônima errada) sem falha-cedo — o comportamento fail-loud só vale para clientes migrados.

#Produtos, templates e reports (sistema de blocos)

#Visão geral

O liquid-dataviz monta dashboards a partir de blocos (canvas) organizados em uma grade de 6 colunas. Um dashboard existe em três estágios: template (molde reutilizável, coleção dashboardTemplates/{id}), report (cópia concreta pertencente a um cliente, em clients/{clientId}/groups/{groupId}/reports/{reportId}) e render em runtime (ReportPage, que busca os dados de cada bloco e desenha a grade). Cada template/report declara productRefs (a que produto pertence, ex.: liquid-play, liquid-play-plus) e metricRefs (quais métricas do catálogo Firestore alimentam seus blocos). O produto é usado para gating na galeria de templates (só aparecem templates cujos productRefs intersectam os produtos contratados pelo cliente) e para escopar o fetch de dados ao produto de origem do report.

O coração do modelo é o par blockMap + layout: blockMap é um dicionário { blockId -> CanvasBlock } com a configuração de cada bloco (tipo, título, metricId, formatação, colSpan…), e layout é uma lista de linhas (CanvasRow[]), cada uma com uma lista ordenada de blockIds. O renderer desenha cada linha como um grid grid-cols-6 e posiciona cada bloco com col-span-N conforme o colSpan do bloco (src/pages/report/ui/ReportPage.tsx:355-369, grid-cols-6 na linha 357). Os blocos em si não contêm dados no template — só carregam metricId; os dados são resolvidos em runtime por useReportData via POST /api/metrics/batch (recipe → Data Contract → binding do cliente → BigQuery).

Os 23 templates canônicos vivem como código em scripts/templates/*.template.mjs (10 do Liquid Play + 13 do Covenants v2) e são publicados em Firestore por scripts/seed-play-templates.ts (scripts/seed-play-templates.ts:50-55). O runtime nunca lê os .mjs: ele lê dashboardTemplates/{id} do Firestore (src/shared/config/dashboard-templates.ts:6-14 documenta que o array hard-coded antigo de 40 templates e seus seeds foram removidos). Reports de cliente são criados copiando um template (galeria, ou seeds como scripts/seed-vila-rosa-reports.mjs).

#metricPageFilters (filtros de página)

Declarados em template.filters.metricPageFilters (schema CanvasPageFilters, types.ts:357-392). Cada entrada é { kind: 'date_range'|'snapshot'|'in', attribute, control?, label?, labelAttribute? }. useReportData compõe o objeto pageFilters enviado ao /api/metrics/batch a partir dessas declarações (useReportData.ts:308-328):

  • date_range → { kind:'date_range', start, end, attribute }.
  • snapshot → { kind:'snapshot', value: end, attribute }.
  • in sem control → alimentado pelo filtro global de projetos.
  • in com control: 'dropdown' → alimentado pela seleção local do usuário (pageFilterValues?.[key]); vazio = no-op (1=1) no resolver.

Quando o template não declara metricPageFilters, usa-se o default contratos.data_base_report para date_range e snapshot (useReportData.ts:220-223). A entidade dos ambient filters é derivada do attribute do primeiro filtro declarado (useReportData.ts:333).

PageFilterBar renderiza um MultiSelectCombobox por entrada in+dropdown (src/widgets/page-filter-bar/ui/PageFilterBar.tsx:32-73), buscando as opções via POST /api/metrics/filter-values (PageFilterBar.tsx:50-64). label vira o rótulo do dropdown e labelAttribute permite exibir um rótulo amigável mantendo attribute como chave real (types.ts:381-390). Estado e reset. usePageFilterValues(resetKey, initialValues) (src/shared/hooks/usePageFilterValues.ts) guarda a seleção dos dropdowns e a reseta quando resetKey muda. ReportPage usa resetKey = ${clientId}|${groupId}|${reportId} (ReportPage.tsx:91-94) — sem isso, como o App Router reaproveita o componente na troca de rota, a seleção vazaria entre reports (chaves genéricas como "banco"/"categoria" se repetem entre templates, usePageFilterValues.ts:10-31).

Implementado em src/pages/report/ui/drill-through.ts (funções puras). Fluxo:

  1. Serialização de saída. serializePageFilters(values) transforma a seleção dos dropdowns em querystring pf.<attribute>=v1,v2&... (chaves vazias omitidas, drill-through.ts:21-28). ReportPage calcula essa string (ReportPage.tsx:254-257).

#Observações e possíveis inconsistências

  1. Os 10 templates Liquid Play referenciam um produto (play) que não é o produto ativo (liquid-play) — ficam escondidos na galeria para clientes com productBindings. Todos os templates play declaram productRefs: ['play'] (grep em scripts/templates/*.template.mjs: contratos:109, detalhamento:26, pagamentos:36, fluxo-caixa:23, pdd:33, pricing:53, simulacao-ltv:39, inadimplencia:179, repasse:41, visao-geral:17). Mas os produtos ativos são liquid-play/liquid-play-plus (seed-liquid-play-contracts.mjs:235-258) e o produto play foi renomeado para play-legacy e arquivado (seed-liquid-play-contracts.mjs:348-373). No gating da galeria (TemplateGallery.tsx:116-135), um cliente com bindings tem clientProductIds = {liquid-play, liquid-play-plus}; como ['play'] não intersecta esse conjunto, os 10 templates play são ocultados. Só apareceriam para clientes legacy (sem productBindings). productRefs é soft/não-bloqueante no save (src/shared/lib/firestore/dashboard-templates.ts:65), então o seed grava esses templates mesmo com a ref órfã. (Não encontrei nenhum alias play→liquid-play no código: grep por 'play'/normalizeProduct em src/ só retorna fixtures de teste.) É o análogo vivo da preocupação histórica com templates covenants v1 ['covenants'].

  2. Não existem mais templates covenants v1 (productRefs: ['covenants']) no conjunto canônico. O array hard-coded antigo de ~40 templates e seus seeds foram removidos (src/shared/config/dashboard-templates.ts:6-14); o conjunto atual são os 23 de seed-play-templates.ts (10 play + 13 covenants-v2, todos ['liquid-play-plus']). As refs ['credit']/['covenants'] só sobrevivem em fixtures de teste (src/shared/schemas/__tests__/dashboard-template.test.ts:12, 38,53). Os covenants v2 (['liquid-play-plus']) são visíveis ao Galli e à Vila Rosa (ambos têm binding liquid-play-plus).

  3. Gauge nunca escala percentuais — footgun latente. Nem useReportData (branch gauge, useReportData.ts:182-189) nem GaugeBlock.formatGaugeValue (GaugeBlock.tsx:25-33) multiplicam por 100, enquanto KPI/table format:'percent' multiplicam (useReportData.ts:41-43; TableBlock.tsx:42-44). Um gauge ligado a uma métrica razão 0-1 com threshold na escala 0-100 classificaria sempre como vermelho. Os templates já contornam isso (certidões/inadimplência usam KPI percent em vez de gauge; obra usa 0-100 cru), com o motivo documentado nos comentários (covenants-v2-visao-executiva.template.mjs:12-18), mas nada no schema impede um autor futuro de cometer o erro.

  4. Thresholds de gauge são placeholders "A CONFIRMAR". indice_recebivel e indice_recebivel_estoque usam threshold 1.2 / warnThreshold 1.5 marcados "THRESHOLD A CONFIRMAR com o contrato do Inter" (covenants-v2-visao-executiva.template.mjs:100,105); o desvio de obra usa -5/-2 também "A CONFIRMAR" (covenants-v2-evolucao-obra.template.mjs:63-65); os alertas de inadimplência (alertThreshold 5 e 3) idem (covenants-v2-inadimplencia.template.mjs:49-54). Ou seja, o verde/âmbar/vermelho exibido pode não refletir o covenant contratual real.

  5. RATING_STATUS_MAP (A–H) do Mapa de Vendas é convenção ilustrativa, não semântica de domínio. A/B=success, C/D/E=warning, F/G/H=danger (covenants-v2-mapa-vendas.template.mjs:24-28), com o próprio comentário afirmando que o Looker original só usa paleta categórica sem status (covenants-v2-mapa-vendas.template.mjs:5-9). O verde/vermelho no rating pode induzir leitura de "bom/ruim" que o domínio não estabelece.

  6. A galeria não conta blocos donut nem gauge no breakdown. summarizeBlocks só acumula kpi/kpis, chart e table (TemplateGallery.tsx:54-69); totalBlocks conta tudo via Object.keys (TemplateGallery.tsx:153). Em covenants-visao-executiva (2 gauges + 1 donut) os badges "KPIs/gráficos/tabelas" somam menos que o total de blocos exibido, sem os gauges/donut aparecerem em nenhuma seção.

  7. CHART_TYPE_LABEL da galeria não mapeia waterfall. O mapa cobre bar/line/area/composed/stacked-bar (TemplateGallery.tsx:71-77), então um gráfico waterfall (ex.: extrato resumido em visao-executiva) exibe o rótulo cru waterfall na lista de gráficos do painel de detalhe.

  8. Cores hardcoded em ChartBlock não trocam no tema claro. As reference lines, a zero-line e a base do waterfall usam rgba(255,255,255,...) (ChartBlock.tsx:95-97, 146-147), e o tooltip do waterfall usa fill:'rgba(255,255,255,0.5)'. Conforme o CLAUDE.md, cores hardcoded não seguem os tokens semânticos — no tema claro (que existe via next-themes) essas linhas/labels tendem a ficar quase invisíveis.

  9. Mudança em template não propaga para reports já criados. O import é um deep-copy pontual (TemplateGallery.tsx:157-176; seed-vila-rosa-reports.mjs:100-119) e o re-seed sem --force pula reports divergentes como "conflito" (seed-vila-rosa-reports.mjs:191-199). Atualizar os 13 reports da Vila Rosa após editar um template exige re-seed com --force (ou re-import manual). Não há mecanismo de "sincronizar template → reports" na UI.

  10. flattenKpiBlocks/migratePage regrupa KPIs em linhas de 3, ignorando colSpan — mas não afeta o ReportPage. A migração explode kpis e reparte em linhas de no máximo 3 blocos (types.ts:473-475), o que contradiria o layout de 6 colunas com colSpan explícito. ReportPage renderiza report.layout diretamente (ReportPage.tsx:356), sem chamar migratePage, então reports de template não são afetados; o risco existe só no caminho de canvas/explore que consome páginas legadas. Vale confirmar que nenhum fluxo de report passa por essa migração.

  11. queries é aceito e persistido mas ignorado na renderização. useReportData recebe _queries e explicitamente o descarta (useReportData.ts:227-240), e o schema marca TemplateQueryConfig como legado. Templates/reports que ainda carregam queries mantêm um campo morto — toda a busca de dados hoje passa por metricId + /api/metrics/batch.

#Frontend: páginas, widgets e experiência

#Visão geral

O liquid-dataviz é um dashboard Next.js 16 (App Router) para visualização de dados de securitização de crédito imobiliário, com suporte multi-cliente e backend em BigQuery/Firestore. A camada de rotas fica em app/, organizada em route groups: (dashboard)/ (páginas protegidas de negócio), (admin)/ (back-office), além das rotas de topo app/login, app/docs, app/page.tsx (landing) e as páginas de erro app/not-found.tsx / app/error.tsx. Toda a lógica de UI vive em src/ seguindo um padrão feature-sliced: app/**/page.tsx são wrappers finos que renderizam componentes de src/pages/*/ui/*; blocos reutilizáveis de dashboard estão em src/widgets/*; componentes de design-system (shadcn/ui, New York) em src/shared/ui/*.

O ponto arquitetural mais importante para esta documentação é que as 10 páginas "clássicas" de dashboard (/dashboard, /contratos, /detalhamento, /elegibilidade, /fluxo-de-caixa, /pagamentos, /pdd, /pricing, /repasse, /simulacao) não têm mais componentes nem hooks dedicados. Todas renderizam o mesmo componente genérico RouteTemplatePage (src/pages/dynamic/ui/RouteTemplatePage.tsx), variando apenas um templateId. O conteúdo (KPIs, gráficos, tabelas) é declarado em templates canônicos persistidos no Firestore e carregado em tempo de execução; os blocos são preenchidos por uma pipeline única de métricas (useReportData → POST /api/metrics/batch). O mesmo motor de canvas (CanvasBlockRenderer / CanvasPanel / useCanvasStore) é reutilizado em quatro contextos: Explore (canvas conversacional), ReportPage (relatórios salvos, com edição), RouteTemplatePage (consumo das páginas clássicas) e TemplateEditorPage (autoria no admin).

A experiência é dark-first (tema escuro default via next-themes), com um tema claro completo por overrides de variáveis CSS OKLch, um assistente de IA (AISidebar) montado como corpo principal da barra lateral de navegação no desktop, filtros globais em dois níveis (globais via DataProvider e por-página via PageFilterBar), e exportação de página para PDF via captura headless (puppeteer) + montagem com jsPDF.

#Visão geral

A camada de IA é um sistema multi-agente para análise de carteiras de securitização de crédito imobiliário. Há dois orquestradores distintos, cada um servindo uma superfície da UI: o orquestrador analítico (chat conversacional na AISidebar, via /api/chat) e o canvas orchestrator (construção de dashboards/relatórios no modo edição, via /api/canvas-chat). Ambos compartilham o mesmo catálogo de ~57 tools, o mesmo model registry (Vertex Gemini) e o mesmo pipeline de memória/RAG sobre Firestore.

O runtime está em migração parcial de AI SDK v6 puro para Mastra runtime full (ADR-0014, supersede ADR-0002). O /api/chat já foi reescrito para construir uma instância Mastra por requisição e delegar a Agent.stream (app/api/chat/route.ts:35,:135,:145); os 8 sub-agentes têm versões Mastra em src/features/ai-agents/mastra/*. O canvas orchestrator continua em AI SDK v6 puro (streamText + stepCountIs(30) + prepareStep, src/features/canvas-orchestrator/orchestrator.ts:242-243), assim como o orquestrador analítico legado (src/features/ai-agents/orchestrator.ts:125), que permanece no código mas não é mais chamado pela rota de chat.

A configuração dos agentes deixou de ser hardcoded e passou a ser data-driven via AI Studio (ADR-0016/0017): coleções Firestore aiAgents, aiSkills, aiWorkflows, knowledgeBases, semeadas por um manifest (src/features/ai-studio/seed/manifest.ts) e editáveis por admin. O runtime sempre lê a config e cai num baseline em código quando ela falta (src/features/ai-studio/runtime/resolve-agent.ts:7-18). Todo o storage de config, metadados, memória de IA, embeddings, catálogo SQL e evals é Firestore (ADR-0013, supersede ADR-0004/Postgres+pgvector); BigQuery permanece só para os datasets de cliente e para o registry/invocations de BQML.

#1.1 Instância Mastra e os 8 sub-agentes

#9. Chat: request → stream → useChat, e o bug conhecido

Frontend (src/widgets/ai-sidebar/ui/AISidebar.tsx): usa useChat do @ai-sdk/react com DefaultChatTransport apontando para /api/chat (ou /api/canvas-chat em editMode, :380-382). O transport injeta o token Firebase (:384-397) e captura o header x-thread-id via fetch wrapper (:400-411). O buildBody envia dataset, clientId, filtros, dashboardState, page, threadId, personaId, icpId e as flags (:445-482). O MessageBubble (:114-291) renderiza partes text (markdown) e partes tool-*: para outputs com campo status (yields do async generator), mostra ToolStepIndicator (analyzing, executing_sql, done, awaiting_input → ClarificationOptions, etc.); para outputs estruturados, renderiza InlineDataRenderer. Em editMode, um useEffect traduz tool results de canvas (declare_layout, fill_block, add_slot, …) em mutações no canvasStore (:556-642).

Bug conhecido (em aberto) — chunk de framing de sub-agente vaza cru e quebra useChat. Os conversores Mastra↔AI SDK v6 estão OK (o route.test.ts:35-39 os mocka como pass-through, e o loop de conversão em route.ts:157-174 filtra null mas repassa o que sobrevive). O problema é de runtime: quando o supervisor Mastra emite chunks de framing de sub-agente (start-step/finish-step do agente aninhado), esses chunks são convertidos para uma forma que o useChat do front não reconhece como parte de mensagem válida, e o stream é interrompido. Como o seed cria um workflow default, o caminho supervisor (que produz esses chunks) é o caminho ativo em produção (§1.3). Este bug está registrado na memória do projeto como pendente; não há, no código atual, marcador/skip de teste nem comentário TODO que o descreva — a única mitigação existente é o filtro de null no loop de conversão.
