## Task 16: platform staff, impersonation, platform audit (`694237a`)

- Ports `PlatformStaffRepository` and `ImpersonationSessionRepository`, with Firestore adapters
  (`firestore-platform-repositories.ts`) and in-memory adapters (their writes mirror into the access test store).
- Use cases:
  - `start-impersonation`: `requireImpersonateRight` first (`platform.user.impersonate` + MFA, and never from an
    impersonated token). Refusals are audited `PLATFORM_ACCESS_DENIED` with `errorCode`. Then the target must not be
    the caller (403) and must read the organization (else 404). The session lasts `durationMinutes` (1–60, contract)
    and is written together with `IMPERSONATION_STARTED` in both logs, in one transaction. Tenant entries use actor
    `{ id: targetUid, onBehalfOf: staffUid }`. Returns `createCustomToken(targetUid, { imp, impBy })`, 201 +
    `Location`.
  - `end-impersonation`: only the staff member's own session (else 404). Idempotent: an already ended session
    answers 204 with no second audit entry.
  - `grant-platform-staff`: actor `system`, `PLATFORM_STAFF_GRANTED` on the platform log in the same transaction,
    `createdAt` kept on re-grant, then `syncClaims`.
  - `audit-impersonated-request`: `IMPERSONATED_REQUEST_SERVED`, or `IMPERSONATED_WRITE_DENIED` for a 403 on a
    non-GET. Written to both logs with `onBehalfOf` and metadata `{ endpointId, errorCode? }`. A request whose session
    is unknown is written to the platform log only.
- **Pipeline (`api-route.ts`):** the request scope wraps `authorize` to remember the last denial. On an error
  response the pipeline logs `access_denied { endpointId, reason }`, which answers "reason in logs only". For every
  impersonated principal it calls `ApiRouteDeps.onImpersonatedRequest`. If the audit write fails, the request
  answers 500 (it is never served unaudited).
- **Contract:** `AuditMetadataSchema` gains an optional `endpointId`. This is additive; the catalog and OpenAPI were
  regenerated.
- Routes `platform-routes.ts`, plus web route files `v1/platform/impersonation-sessions` and `.../[sessionId]/end`.
- `CoreServer.platform` (`grantPlatformStaff` is for operator tooling).
- **Script `pnpm platform:grant-staff`** (`scripts/grant-platform-staff.ts`, `scripts/src/staff/grant-staff-args.ts`):
  - Flags: `--project --email --role --confirm`. `--confirm` must equal `--project`. Unknown or repeated flags are
    refused. Errors never echo the email.
  - `APP_ENV=local` only targets `demo-*` projects, and remote environments never target them.
  - Uses ADC outside local, looks the uid up by email, and prints the uid only.
  - Smoke-tested against the emulator: grant ok, a wrong `--confirm` refused, 1 `PLATFORM_STAFF_GRANTED` entry
    written.
  - `@core/services` re-exports `PLATFORM_ROLES`, `PlatformRoleSchema` and `UserIdSchema` for it, so no lockfile
    change was needed.
- `auth-emulator-rest.fixture.ts` gains `signInWithPasswordAndSms`. It calls `signInWithPassword`, then
  `mfaSignIn:start`, reads the code from the emulator's `verificationCodes`, then calls `mfaSignIn:finalize`.

## Task 17: four-eyes approval requests (`776b863`)

- `domain/approval-state.ts` holds the pure transitions and the effective status (a pending request past
  `expiresAt` → expired). New errors: `SelfApprovalForbiddenError` and `approval-errors.ts` (NOT_FOUND, CONFLICT,
  UNKNOWN_APPROVAL_ACTION, APPROVAL_NOT_REQUIRED, VALIDATION_FAILED with details).
- `ApprovalActionHandler { kind, inputSchema, execute(input, { request, requester, approver, requestId }) }`.
  `approval-handler-registry.ts` erases the input type behind the handler's own schema (no casts). **The registry
  stays open:** `CoreServer.approvals.handlers.register(handler)` works after composition, so SP3 can register
  `agent-command` and SP5 its workflow handler. `createCoreServer({ approvalHandlers })` accepts handlers known at
  startup. Duplicate or malformed kinds throw `ApprovalHandlerRegistryError`.
- Use cases:
  - `request-approval`: route and in-process `requestApproval` (`access` is optional for SP3). It checks the path
    tenant, refuses impersonation, requires the caller's own `authorize()` on the permission,
    `requiresApproval` (else 422 `APPROVAL_NOT_REQUIRED`), a handler (else 422), and a valid input (400 on
    `action.input.*`). The request is pending for 7 days and audited `APPROVAL_REQUESTED` with `inputHash`.
  - `list-approval-requests`: `core.approval.read`, effective status, same `pending`/`expired` filtering as
    invitations.
  - `approve-request`: four eyes. The requester, and the owner of a requesting API key, get
    `SELF_APPROVAL_FORBIDDEN`. An impersonated caller gets 403. `core.approval.decide` and the action's permission
    are both required (else 403 `FORBIDDEN`), and a caller who cannot read approvals gets 404. One transaction moves
    pending → approved (`APPROVAL_APPROVED`); an expired request is stored as `expired` and answers 409. The handler
    runs once, and a second transaction records approved → executed or failed (`APPROVAL_EXECUTED`/`APPROVAL_FAILED`,
    `errorCode`).
  - `reject-request`: same checks, and records `APPROVAL_REJECTED`.
- Firestore and in-memory repositories; `approvals-routes.ts` with its own error mapping; 3 web route files.
- Indexes `approval-requests tenantId+createdAt desc` and `tenantId+status+createdAt desc`.

## Deviations and concerns

1. **TDD order in Task 17.** The domain and registry tests were written with their code. The approval use cases
   were written before `approval-use-cases.test.ts` (14 tests, all passing on first run). The three emulator tests
   were written after their code.
2. **Approval composition.** The plan's `createAccessServices({ permissions, approvalHandlers })` became a separate
   `access/approval-composition.ts` (`createApprovalServices`, `createFirestoreApprovalServices`), exposed as
   `CoreServer.approvals`, with `createCoreServer({ approvalHandlers })`. This leaves the access write-side signature
   untouched, and the registry stays open for late registration.
3. **SP3 adapter needed.** SP3's `ApprovalPort.requestApproval({ principal, node, permission, action:
   AgentApprovalRequest })` must map onto SP1's `requestApproval({ principal, input: { node, permission, action: {
   kind: "agent-command", input, summary } }, requestId })`. The call returns a `Result`, so SP3 turns `ok: false`
   into its fail-closed `APPROVAL_UNAVAILABLE`, and `approvalId` = `data.id`. The handler context gives
   `{ request, requester, approver, requestId }`; SP3's `idempotencyKey` lives in its own action input
   (`runId:toolCallId`).
4. **At-most-once execution.** A crash between the approve transaction and the execution record leaves the request
   `approved` and never re-executed. This is deliberate. Nothing sweeps these requests yet (SP5 inbox can show them).
5. **Impersonation choices not in the spec.**
   - Staff cannot impersonate themselves (403).
   - The target must currently read the organization (404 otherwise).
   - Only the staff member who opened a session can end it (a `platform-admin` cannot end someone else's).
   - Every impersonated request costs one session read and two audit writes.
6. **The pipeline's `access_denied` log** covers every `/v1` denial, not only impersonation. It records the last
   `authorize()` denial of the request. It is info level and contains no PII.
7. **Script re-exports.** `@core/services` re-exports three contract symbols for the grant script, which avoided a
   lockfile change while SP2 holds `pnpm-lock.yaml` WIP.
8. **Shared files with SP2 WIP.**
   - `composition.ts` conflicted three times in `git merge-file`. Each time I resolved it by keeping SP2's
     module-settings hunk and adding `platform, approvals, auditLogs` to its `buildCoreRoutes` call.
   - `services/src/index.ts`, `app/package.json`, the catalog JSON and `openapi/v1.yaml` merged cleanly into the
     working tree.
   - Nothing of SP2's was staged: commits were built in `wt-sp1-t16` and staged index-only after checking that the
     shared index was empty.
   - SP3 committed `a48105a`, `af12b11` and `e527e04` meanwhile; my commits were rebased onto them without
     conflicts.
9. **Flaky test.** `scripts/src/dev/process-tree.test.ts` "kills each child together with its grandchildren" failed
   once under full-suite load (6 s). It passed alone and in the final full run.
10. **`firestore.rules` untouched (Task 19).** `impersonation-sessions`, `platform-staff` and `approval-requests`
    are denied by default.
