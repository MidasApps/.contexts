## Task 7: request context, route allowlist, runtime composition

### `@core/agents`

**`context/write-agent-context.ts`**
- `buildAgentRequestContext` builds the context from the `FirebaseMastraAuth` principal. It
  returns `null` when there is no membership, tenant or regional settings.
- `writeAgentContext` writes one key per `AgentRequestContext` field, plus `corePrincipal`,
  `MASTRA_RESOURCE_ID_KEY` (`tenantId:uid`) and `MASTRA_THREAD_ID_KEY` (when there is a
  conversation).
- `clearAgentContext` removes every key the middleware owns.
- `AgentRuntimeContextSchema` is each agent's `requestContextSchema`. It is a `looseObject` because
  Mastra keeps `user` and `mastra__*` in the same context.

**`auth/context-middleware.ts`**
- Mastra runs `server.middleware` before its per-route auth, so the middleware authenticates
  through the same provider.
- `FirebaseMastraAuth` now memoizes by raw `Request` (WeakMap), so a request is verified once.
- The middleware always clears client-sent keys first. Mastra merges the body `requestContext`
  into the context, and this is what stops it.
- With no principal or no membership it writes nothing, and Mastra answers 401 or 403. A verify
  error counts as "no principal".
- `X-Request-Id` goes through `resolveRequestId`, so it is either a valid ULID or a new one.
- New forwarded header `X-Conversation-Id` (`FORWARDED_HEADERS.conversationId`). It is validated
  against `^[A-Za-z0-9_-]{1,128}$` and sets the memory thread.

**`auth/route-allowlist-middleware.ts`** returns 404 for every built-in route under the prefix
except these:

| Group | Allowed |
|---|---|
| `/agents` | GET the list and a single agent |
| `/agents/:id` | POST `generate`, `stream`, `approve-tool-call`, `decline-tool-call` (and their `-generate` forms), `resume-stream` |
| `/memory` | GET only; DELETE on `threads/:id` |
| `/workflows/*`, `/schedules/*` | all methods |
| MCP | `mcp`, `sse`, `messages` (the protocol endpoints); GET `tools` and `resources` |
| `/observability/*`, `/datasets/*` | all methods |

Closed routes include:
- `/vectors`, `/vector` and `/tools`;
- `/agents/:id/tools/:id/execute`, `/agents/:id/model*` and `clone`;
- `/v1/responses` and `/v1/conversations`;
- `/stored/*`;
- memory writes;
- MCP REST tool execution.

Because it is an allowlist, any route a Mastra upgrade adds stays closed until someone lists it.

## Task 8: `MastraGateway`

All files are in `packages/services/src/services/agents/`.

**Port.** `application/ports/agent-runtime-gateway.ts` defines `AgentRuntimeGateway` with
`generate`, `stream`, `approveToolCall`, `declineToolCall`, `startWorkflow`, `resumeWorkflow`,
`streamWorkflow`, `listThreadMessages`, `deleteThread` and `callMcp`. The call scope is resolved
by `/v1`, not taken from a body. Results are `{ ok, data } | { ok: false, error: { code, status, retryAfterSeconds? } }`.

**`adapters/driven/mastra-gateway.ts` and `mastra-request.ts`**
- JSON calls use `@mastra/client-js`: generate, workflow `createRun` + `startAsync` /
  `resumeAsync`, and thread messages and delete.
  - It builds one client per call, because the headers carry that caller's credential.
  - `retries: 0`, because the SDK would otherwise re-run a failed generate on a 5xx.
- Streams use raw `fetch` for agent streams, tool approve/decline (their routes stream), workflow
  streams and MCP (`accept: application/json, text/event-stream`).
- Headers come from `FORWARDED_HEADERS`, and `runId = requestId`.
- The run options `requestContext`, `runId`, `resourceId`, `threadId`, `resource` and `thread`
  are always stripped.
- Deadlines: 120 s for JSON calls; 30 s to the first byte for streams. After that the body streams
  under the caller's signal only.
- If the caller aborts, the call rejects with the caller's reason and the upstream request is
  closed (tested).

**`adapters/driven/mastra-error-mapper.ts`** maps by status only and never reads the body:

| Mastra | Gateway |
|---|---|
| 401 | `UNAUTHORIZED` 401 |
| 403 | `FORBIDDEN` 403 |
| 404 | `NOT_FOUND` 404 |
| 400, 422 | `VALIDATION_FAILED` 400, no details |
| 409 | `CONFLICT` 409 |
| 429 | `RATE_LIMITED` 429, numeric `Retry-After` kept |
| anything else, or a network error | `UPSTREAM_UNAVAILABLE` 502 |
| deadline | `UPSTREAM_UNAVAILABLE` 504 |

`gatewayErrorResponse` builds the `api.md` §6 envelope through SP1's `apiError`.

**`adapters/driven/serverless-id-token.ts`** mints the `X-Serverless-Authorization` value with
`google-auth-library` (`GoogleAuth().getIdTokenClient(audience)`, then `getRequestHeaders()`). It
is used only outside local; pass `serverlessToken: null` in local. If minting fails the call
returns 502 and Mastra is not called.

**Web env** (`apps/web/src/web-env.schema.ts`):
- `MASTRA_URL` defaults to `http://localhost:4111` in local. Outside local it is required and
  must be https.
- `MASTRA_AUDIENCE` is required outside local.
- `.env.example` documents both.

## Task 12: knowledge tables, row security, use cases

**Tables** (`knowledge/adapters/driven/drizzle-schema.ts`, the source for migrations):
- `ai.documents` has the spec §11 columns. It is unique on `(tenant_id, source, source_ref)` and
  on `(id, tenant_id)`, indexed on `(tenant_id, namespace)`, and has CHECKs on `source`,
  `status` and `content_hash`.
- `ai.chunks_v1` has a `vector(1536)` column (`embedding`). It has:
  - a composite FK `(document_id, tenant_id)` to `documents(id, tenant_id)` with
    `ON DELETE CASCADE`, so a chunk cannot point at another tenant's document;
  - unique `(document_id, chunk_index)`;
  - indexes on `document_id` and `(tenant_id, namespace)`;
  - HNSW `vector_cosine_ops` with `m=16, ef_construction=64`.

**Migrations**
- `0003_knowledge_tables.sql` (generated) creates the tables, indexes and RLS. Each table gets two
  policies:
  - `*_tenant_rows`: `FOR ALL`, with `USING` and `WITH CHECK` `tenant_id = current_setting('app.tenant_id', true)`;
  - `*_platform_read`: `FOR SELECT` on `_platform` rows.

  So a tenant reads `_platform` rows but can never write them. The HNSW index is built without
  CONCURRENTLY because the table is new and empty, and the migrator runs in a transaction.
- `0004_knowledge_runtime_role.sql` (custom) sets `FORCE ROW LEVEL SECURITY`. It creates
  `knowledge_runtime` (NOLOGIN, NOBYPASSRLS, DML on the two tables only), grants it SET-only to
  `mastra_runtime` and to the migrator (for the Postgres tests), and revokes everything from
  PUBLIC.
- `drizzle-kit generate` afterwards reports "No schema changes". I recorded this as the
  2026-09-30 amendment of decision 0022.

**`postgres-knowledge-repository.ts`**
- Every call is one `withTenantTransaction` followed by `SET LOCAL ROLE knowledge_runtime`, so the
  policies apply even for a superuser login such as the local one.
- Upsert: `SELECT ... FOR UPDATE`, then `INSERT ... ON CONFLICT DO UPDATE`. `unchanged` means the
  same hash and namespace on a document that is already `ready`; any other change sets it back to
  `pending`.
- Replace: lock the document, then delete, insert and mark it `ready`, all in one transaction. A
  platform document is never lockable by a tenant.
- Search: `SET LOCAL hnsw.iterative_scan = relaxed_order` (pgvector 0.8.6), then a CTE with
  `ORDER BY embedding <=> $1 LIMIT k` over namespace and `embedding_model` filters, then a join
  to `ready` documents.
- Vectors become `[x,...]` literals only after a check for 1536 finite numbers.

**Use cases** (`application/use-cases/`) are register, replace, search, delete and list, with
server-only input schemas in `knowledge-input.schema.ts`:
- `_platform` documents use the `catalog` and `module:*` namespaces; tenants use `tenant` and
  `project:*`.
- Chunk indexes must be exactly 0..n-1.
- `topK` is 1–20 and `limit` is 1–100.
- `sourceUrl` must be https.
- Search returns `knowledge.Citation` objects: `kb:<id>#<n>`, score = 1 − distance rounded to 4
  places, results under 0.3 dropped.

**Mastra binding.** `KnowledgePort` is bound in `create-runtime-ports.ts` with
`AI_MODEL_EMBEDDING` as the model filter (`knowledge-port-binding.ts`).

**Postgres test** (`postgres-knowledge-repository.postgres.test.ts`, 10 cases):
- upsert is idempotent and flags unchanged content;
- replacing chunks is atomic (a failing insert keeps the old chunks);
- tenant A never gets tenant B's chunk, even with the same text;
- `_platform` rows are visible to both tenants but a tenant cannot replace or delete them;
- `WITH CHECK` refuses a forged `_platform` insert;
- the namespace filter works;
- delete cascades to chunks;
- with no tenant setting only `_platform` rows are visible;
- `EXPLAIN` shows `chunks_v1_embedding_hnsw`, with seq scans and sorts disabled because a few test
  rows make a sort cheaper;
- replace + search through the use cases returns citations and drops weak ones.

## Deviations and concerns

1. **Regional settings are fail-closed until SP1 Task 12.** `resolveAccessContext` is an interim
   adapter, and its regional port rejects, so real Mastra requests answer 401 today. Bind
   `resolveAccessContext` in `create-runtime-ports.ts` when SP1 exports it.
2. **SP1 audit entries have no metadata field.** The input hash, error code, fingerprint, agent id
   and outcome detail are dropped. `failed` and `pending-approval` are recorded as `success`
   entries of an attempted action. SP1 should add a small field of safe keys, or an outcome enum.
3. **Mastra adds `resourceId` (`tenantId:uid`) to span metadata by itself.** The uid is personal.
   Task 17 (OTLP export) should hash or drop it.
4. **The route allowlist may hide some Studio panels in local dev** (tool lists, `/stored/*`,
   `/system/*`). This is on purpose. `mastra dev` Studio was not exercised.
5. **The gateway uses SP1's `UNAUTHORIZED` code**, not the spec's `UNAUTHENTICATED`, so `/v1` stays
   consistent. A Mastra 400 or 422 becomes `VALIDATION_FAILED` with no details.
6. **`@mastra/client-js` brings `@mastra/core` into `@core/services`' dependency graph.** Web
   server bundles will include it once a route uses the gateway. It also triggers a peer warning:
   `@ai-sdk/ui-utils` 1.2.11 wants zod ^3 (types only).
7. **MCP.** `callMcp` does not forward `mcp-session-id`. Task 24 must choose serverless MCP or
   forward the session header.
8. **`knowledge_runtime` is granted only to `mastra_runtime` and the migrator.** Task 14
   (`/v1/knowledge`, web) and ingestion need the same SET grant for their login roles. The Cloud SQL
   privilege path was not checked remotely.
9. **The emulator test is in-process.** It runs `createNodeServer` with in-memory SP1 readers and a
   regional stub. The built server was only smoke-checked by hand, with the results listed above.
10. **TDD order.** Red was observed first for:
    - the catalog amendment;
    - the auth memo;
    - the web env tests;
    - the knowledge Postgres test (missing modules).

    The middleware, allowlist, compose, gateway and binding tests were written with or just after
    their code and passed on their first run.
11. **SP1 Task 9 landed during this run.** `createCoreServer` now wires Firestore access readers
    by default, so `authorize` in Mastra is real. Only regional settings (1) remain interim.
