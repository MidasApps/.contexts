## Task 16: usage ledger, budget guard, BigQuery sink

### `usage` context (`packages/services/src/services/usage`)

**Tables.** `drizzle-schema.ts` defines two tables (migration `0006_usage_tables.sql`, generated):

- `usage.llm_calls`:
  - the columns of spec §12, plus `created_at` and `updated_at`;
  - `cost_micro_usd bigint` is nullable;
  - index on `(tenant_id, occurred_at)`;
  - CHECKs on tokens, cost, latency and the trace-id format.
- `usage.tenant_budgets`: unique `tenant_id`, and `monthly_micro_usd` / `monthly_tokens` as `bigint`.

Both tables have a `*_tenant_rows` policy (`FOR ALL`, `USING` and `WITH CHECK` on `app.tenant_id`). There are no
platform rows.

**Migration `0007_usage_runtime_role.sql`** (custom):

- `FORCE ROW LEVEL SECURITY` on both tables.
- View `usage.tenant_month_spend` with `security_invoker = true`, so the view applies row level security too.
- Role `usage_runtime`: NOLOGIN, NOBYPASSRLS.
  - It has SELECT and INSERT on the ledger. It has no UPDATE or DELETE, so the ledger is append-only.
  - It has SELECT, INSERT and UPDATE on budgets, and SELECT on the view.
  - `mastra_runtime`, `web_runtime` and the migrator may `SET ROLE` to it.
- `pnpm db:migrate` ran twice. `drizzle-kit generate` then reports "No schema changes".

**`domain/budget-policy.ts`** is the single source of the caps:

- The plan default is USD 50 (50 000 000 micro-USD) and 20 M tokens per month.
- Each cap falls back to that default on its own when it is missing, zero, negative, fractional or not a safe
  integer. It never falls back to "no cap".
- The alert threshold is 80 %.
- `evaluateBudget` refuses when either cap is reached, and alerts at 80 % of either cap.
- The table of the caps in force is in the decision 0026 amendment.

**Use cases:**

- `recordLlmCalls`: the rows cross `usage.LlmCall` once, with at most 500 per batch. A refused batch answers
  `VALIDATION_FAILED` with field details.
- `checkTenantBudget`: checks the UTC month. Input and output tokens count against the token cap.
- `getUsageSummary`: returns the `usage.UsageSummary` contract, broken down by model.

**Postgres repository.**

- Every call is one `withTenantTransaction` followed by `SET LOCAL ROLE usage_runtime`.
- Inserts run one transaction per tenant, with `ON CONFLICT (id) DO NOTHING`, so a retried batch never counts
  twice.
- The budget check reads an indexed `occurred_at` range. The view serves reports.

**Sinks.**

- `bigquery-usage-sink.ts`:
  - maps rows to the `ai_observability.llm_calls` columns of bigquery.md §14;
  - adds `llm_call_id`, `trace_id`, `agent_id` and `provider`;
  - `tool_calls` is `[]` and `error` is `null`;
  - `insertId` is the row id, in batches of 500 with `raw: true`;
  - it loads the SDK lazily.
- `noop-usage-sink.ts` writes the log line `usage_export_skipped`.
- `createUsageSink({ kind })` picks one from `USAGE_SINK`.

### `@core/agents`

**`observability/usage-ledger-exporter.ts`** turns every ended `MODEL_GENERATION` span into one row:

- The id is a uuidv7 (`observability/uuidv7.ts`).
- Tenant, user and request id come from the span's **request-context snapshot**, not from span metadata. The
  probe showed that a body `tracingOptions.metadata.tenantId` overrides the root span's metadata.
- The provider vendor is the part before the dot (`google.generative-ai` becomes `google`).
- The cost comes from `model-prices.ts`. A missing price stores `null` and logs `usage_price_missing` once per
  model.
- It flushes after 2 s or 50 rows.
- It never throws:
  - a failed write is logged (`usage_ledger_flush_failed`);
  - the rows are retried on the next flush, with a buffer of at most 1000 rows (`usage_ledger_rows_dropped`).
- A span without a tenant is skipped and logged (`usage_span_without_tenant`).

**`processors/tenant-budget-guard.ts`** runs `processInput` once per run:

- `BUDGET_EXCEEDED` aborts with `{ processorId: "tenant-budget-guard", code }`.
- A port failure, or a missing server context, aborts with `BUDGET_UNAVAILABLE` (fail-closed).

### `apps/mastra`

## Task 17: guardrail profile and observability

### `processors/guardrail-profile.ts`

`createGuardrailProfile({ models, ports }, kind)` builds the processor stacks.

**`entry` input stack**, in order:

1. `UnicodeNormalizer`.
2. `TenantBudgetGuard`. It runs before any detector, so a tenant over its cap spends nothing on detection.
3. `PromptInjectionDetector`: block, threshold 0.8.
4. `ModerationProcessor`: block.
5. Tenant PII detector: `warn` or `redact`, per run, from `agent-settings`; an error means `redact`. It checks
   the last message only.
6. `TokenLimiterProcessor`: 60 000 tokens, best-fit.
7. `TokenCostControl`, only when the flag is on.

The LLM detectors use the `fast` role with `errorStrategy: 'strict'`.

**`entry` output stack:**

- `SystemPromptScrubber` on the final answer only. On the stream it calls the model once per text delta.
- `RegexFilterProcessor` with the `secrets` preset, redacting.

**`delegated`** (for the subagents of Task 20) is the normalizer, the budget guard, the token limiter and the regex
filter.

**Wiring.** `AgentFactoryDeps.guardrails(kind)`. Ping and knowledge use `entry`, because callers reach them
directly. For knowledge the output stack is the citation guard, then the profile.

### Observability

**`observability/create-observability.ts`.** The exporters are:

- `MastraStorageExporter`;
- `OtelExporter`, only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set (`provider.custom`, `http/protobuf`, traces
  only);
- the usage ledger.

`SensitiveDataFilter` gets the 15 defaults, copied, plus `idToken`, `cookie`, `setCookie`,
`x-serverless-authorization` and `x-api-key`. `requestContextKeys` adds `conversationId`.

**`observability/span-export-policy.ts`** decides what storage and OTLP receive, through a `customSpanFormatter`:

- `metadata.resourceId` becomes `sha256:<16 hex>`, and `metadata.userId` is dropped (concern 3 of report
  task-7-8-12);
- the request-context snapshot keeps only the span context keys;
- OTLP carries no `input` or `output` outside local and dev.

Sampling happens **per exporter**: a deterministic 20 % of trace ids outside local and dev (`sampleTraces`). The
instance itself samples every trace and sets `includeInternalSpans: true`. A probe showed that detector calls run
in internal `MODEL_GENERATION` spans; the ledger now bills them (`agentId` = the processor id). A compose test
checks this.

**`observability/trace-context.ts`:**

- `parseTraceparent` follows W3C level 1.
- `withServerTracingOptions` rewrites a JSON body: it drops the client `tracingOptions` and sets
  `{ traceId, parentSpanId }` from `traceparent`.
- The context middleware applies it before authentication. Mastra 1.71's `getParams` reads
  `c.req.raw.clone().text()`.
- The gateway also strips `tracingOptions` (`SERVER_OWNED_KEYS`).

Log correlation needs no code: `PinoLogger.__attachObservability` merges trace ids natively.

**Fake model.** The fake PII verdict now gives offsets relative to the `Content: "…"` part of Mastra's detector
prompt, so redaction works in fake mode.

## Task 18: memory and tenant isolation

**`memory/create-memory.ts`** builds one `Memory` per runtime:

- `lastMessages` 20;
- `semanticRecall`: topK 4, messageRange 1, scope `resource`;
- `workingMemory`: scope `resource`, with `WorkingMemorySchema` (language, tone, recurringGoals; pii personal);
- `generateTitle` on the `fast` role;
- Observational Memory only when `AI_MEMORY_OBSERVATIONAL=true`, on the `fast` role with resource scope.

**Embedder.** `@mastra/memory` accepts only v2 or v3 embedding models, so `memory/embedding-model-v3.ts` gives it a
v3 view of the factory's v4 embedder.

**Vectors.** `PgVector` lives in schema `mastra` (`buildMemoryVectorConfig`), with `disableInit` when
`MASTRA_STORAGE_INIT=skip`. `db:init` creates the index `memory_messages` (1536, cosine, metadata indexes on
`thread_id` and `resource_id`) with Memory's parameters. The existing re-grant covers the table and its sequence.
It ran twice (exit 0), and `mastra_runtime` has INSERT on it.

**Compose.**

- `vector` is a new argument; the memory is built only when it is given.
- `RuntimeParts.memory`, `vectors: { memory }` and `AgentFactoryDeps.memory` are new.
- **No agent attaches the memory yet:** the supervisor (Task 20) will.

**Thread ownership.** The first run of the isolation test showed that Mastra answers **500**, not 403, when
`generate` names a thread of another resource. `auth/thread-ownership.ts` fixes this:

- the context middleware looks up the owner of every thread the request names (`X-Conversation-Id` and
  `/memory/threads/:threadId`);
- a thread of another resource gets 403 `{ error: "Forbidden" }`;
- a lookup failure gets 503 (fail-closed).

**`memory-isolation.postgres.test.ts`** runs a real `createNodeServer` with `PostgresStore` and `PgVector`. One uid
is a member of two tenants. It checks:

- in tenant A, recall and working memory reach the second thread;
- in tenant B, neither reaches the prompt;
- the thread list for B never shows A's threads;
- B naming A's thread answers 403, on generate and on the messages route.

## Deviations and concerns

1. **`TOKEN_COST_CONTROL_ENABLED` is false although the probe passed.** Turning it on means:
   - swapping the Mastra storage to `PostgresStoreVNext`, with its own observability connection and schema;
   - DDL for its signal tables in `db:init`;
   - relying on Mastra's own price table, which is not ours.

   Mastra also documents that store as low-volume only. The hard cap and the 80 % alert already work. This is a
   follow-up if a daily soft signal is wanted.
2. **Sampling is per exporter, not on the instance** (spec §13 says instance ratio 0.2). With instance sampling,
   80 % of model calls would never reach the ledger or the budget. Internal spans are now exported too, which
   means more spans in storage and OTLP.
3. **The system prompt scrubber checks the final answer only.** On the stream it would cost one LLM call per
   delta. The regex filter still redacts secret-shaped strings on the stream.
4. **The settings port is still not wired in `apps/mastra`**, so the tenant PII detector runs in `redact` mode
   there until SP5 binds `agent-settings`.
5. **Detector cost and latency.** Each entry run makes three sequential fast-model calls before the chat model
   (injection, moderation, PII), plus the final-answer scrubber. All four are billed in the ledger.
6. **OTLP to Cloud Trace is unverified.** `provider.custom` sends static headers only. Google's OTLP endpoint
   needs OAuth tokens, so a collector sidecar (or an auth header source) is needed outside local.
7. **The BigQuery sink sends `user_id` raw**, following the canonical §14 table. bigquery.md §15 prefers a hashed
   column; SP5's export workflow should decide this and set policy tags. The table DDL also belongs to SP5.
8. **The ledger buffer lives in process memory.** A crash loses at most about 2 s or 50 rows, and the budget
   undercounts by that much.
9. **The body rewrite depends on Mastra reading `c.req.raw`**, which I checked in `@mastra/deployer` 1.71.
   `trace-context.test.ts` and the middleware test cover it, but no server-level test does yet.
10. **The memory is not attached to any agent yet** (Task 20). The ownership pre-check adds one `mastra_threads`
    read per request that names a thread.
11. **Two failures that are not mine.**
    - SP1's `permission-registry.test.ts` ("gives member, viewer and device…") fails at `HEAD` after
      `d92f38f`.
    - In the main tree, `catalog-reindex.workflow.postgres.test.ts` fails on SP2's uncommitted catalog, which
      adds example module contracts. It passes on the committed tree.
12. **Concurrency.** While my Task 16 files were staged, an SP1 commit (`85cd80a`) briefly included them. SP1
    rewrote it as `735c904` without them. After that I staged and committed right away each time, and checked
    that each commit's diff contains only my paths.
13. **TDD order.** Red was observed first for:
    - the budget policy;
    - the ledger exporter;
    - PII redaction (the fake offsets);
    - the thread 403 (500 before the middleware check);
    - the OTLP test (it first picked an unsampled trace id).

    The other tests were written together with their code and passed on their first run.
