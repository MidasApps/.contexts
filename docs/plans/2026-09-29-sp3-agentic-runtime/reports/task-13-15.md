## Task 13: `files` context

- **Routes** (contracts `files/endpoints.ts`, handlers `files/adapters/driving/files-route-handler.ts`,
  web route files):
  - `POST /v1/organizations/{organizationId}/files` → 201 + `Location: /v1/files/{fileId}`, body
    `files.FileUploadTicket` `{ fileId, upload: { method, url, headers, expiresAt } }`.
  - `GET /v1/files/{fileId}` → `files.StoredFile`.
  - `GET /v1/files/{fileId}/read-url` → `files.FileReadUrl` (5 min), 409 `CONFLICT` until ready.
  - The umbrella writes `POST /v1/files`; the organization is in the path because SP1 routes name
    their organization there and the tenant never comes from a body (decision 0019 amendment).
- **Policy** (`domain/file-policy.ts`): chat attachments take images (png/jpeg/webp/gif ≤ 10 MiB),
  documents (pdf/txt/md/csv/json ≤ 25 MiB), video (mp4/webm/quicktime ≤ 200 MiB) and audio
  (webm/ogg/mp4/wav ≤ 10 MiB); `knowledge` takes documents only. A refusal is
  `400 VALIDATION_FAILED` with `{ field: contentType|sizeBytes, issue: TYPE_NOT_ALLOWED|TOO_LARGE }`.
- **Order** in `requestUpload`: policy check → `authorize(core.file.upload)` → pending record →
  V4 PUT URL (15 min, fixed `Content-Type`, `x-goog-content-length-range: 0,<size>`, path
  `tenants/{tenantId}/files/{fileId}` generated by the server).
- **Read access**: the uploader (while they keep `core.file.upload`), or `core.knowledge.read` holders
  for `knowledge` files; anyone else gets 404.
- **Local**: with `APP_ENV=local` and the Storage Emulator, the ticket is the emulator media-upload URL
  (`method: POST`). The emulator signer refuses to build anywhere else.
- **Validation**: Functions trigger `onFileFinalized` (`apps/functions/src/files/on-file-finalized.ts`,
  `retry: true`).
  - Reads 64 KiB and detects the type with `file-type` 22.1.1 (MIT, pinned).
  - Text types must be UTF-8 without NUL bytes.
  - Checks size against the policy and the declared size, and the object's Content-Type against the
    declared one.
  - Settles the record in a transaction: `ready`, or `rejected` with the object deleted.
  - Emits `FILE_UPLOADED` through a publisher port (a log line until the bus exists).
  - Redelivery is a no-op, and objects without a record are deleted.
- **Server reads**: `readFileBytes` / `getReadyFile` for ingestion and SP4 (only `ready` files of the
  same tenant).
- **Rules**: `firestore.rules` has an explicit `files/{fileId}` deny. The `storage.rules` comment
  explains the signed URLs.
- **Env**: `FILES_BUCKET` (web and Mastra; the local default is `<project>.appspot.com`, required
  outside local; Functions optional).
- **Functions bundle fix**: the codebase could not load in the emulator (this was already broken at
  `HEAD`; healthz failed too). Two changes fix it:
  - `build.ts` gets a `createRequire` banner, for the CommonJS `require` in google-auth-library;
  - the SQL guard imports `libpg-query` lazily, because its WASM loader ran at import.

## Task 14: ingestion, catalog reindex, `/v1/knowledge`

- **`@core/agents` knowledge**:
  - `chunk-document.ts`: my own recursive Markdown/text splitter (2000/200). It is not `MDocument`,
    because `@mastra/rag` pulls the AWS Bedrock SDK and an alpha reranker client.
  - `extract-text.ts`: plain text, Markdown, CSV and JSON; HTML reduced to text; PDF only through the
    `parsePdf` hook, else `UNSUPPORTED_MEDIA`.
  - `embed-chunks.ts`: batches of 64, dimension check.
  - `citation.ts` and `index-document.ts`.
- **`knowledge-ingest` workflow**: resolve-source → extract-text → chunk → store → embed → emit.
  - Retries: 3 attempts, 2 s apart.
  - Every step re-reads the tenant from the typed context, and resolve-source authorizes
    `core.knowledge.write`.
  - Expected failures end the run with `status: failed` and a code.
  - Progress is sent as transient `data-ingest-progress` parts.
  - store (upsert) runs before embed, so vectors never enter the snapshot.
  - The namespace is `project:<id>` or `tenant`.
- **`catalog-reindex` workflow**: one `_platform`/`catalog` document per AI-catalog contract (title =
  contract id, no examples, no sensitive fields). A run with a caller principal is refused
  (`PLATFORM_ONLY`).
- **Ports**: new `files`, `webContent` and `knowledgeEvents` ports; `KnowledgePort` gains
  `registerDocument` and `replaceChunks`.
  - The Mastra bindings are the files services, the knowledge use cases and the log event publisher.
  - `webContent` is fail-closed until Task 23 (Firecrawl); URL runs fail after their retries.
  - The Task 23 hook is the `WebContentPort`, plus the fixture fake used in tests.
- **Embedding model id**: `embedding_model` is `fake/fake-embedding` in fake mode and
  `AI_MODEL_EMBEDDING` in real mode (`embeddingModelIdOf`). Search uses the same id.
- **Routes**:
  - `GET /v1/organizations/{organizationId}/knowledge/documents` (cursor pages);
  - `GET|DELETE .../documents/{documentId}` (new `getDocument` use case);
  - `POST .../knowledge/sources` → 202 `{ data: { runId } }` through the new gateway `launchWorkflow`
    (`run.start`, no wait). A file source must be a ready `knowledge` upload (404 / 409 / 400).
- **Web wiring**: `apps/web/src/server/runtime-routes.ts` builds the files and knowledge routes on the
  core pipeline (Postgres, gateway, SP1 `resolveAccessContext`). `route()` merges them in.
- **Migration `0005_knowledge_web_runtime_role.sql`**: `web_runtime` (NOLOGIN) with SET on
  `knowledge_runtime`. Deploy grants it to the web DB user (README of apps/mastra).
- **Seed**: the `pnpm seed:local` step "knowledge base" runs catalog-reindex in-process and indexes two
  sample docs for `DemoOrgSeed000000001`. It ran twice: the first run indexed 2 samples (catalog 73
  unchanged), the second 0 indexed, all unchanged.

## SP1 bindings (controller note)

- The `apps/mastra` access port uses SP1 `resolveAccessContext` (`CoreServer.resolveAccessContext`). The
  interim regional adapter is removed, so real agent requests no longer answer 401. Unit tests cover
  mapping, null and error propagation.
- The audit port maps pipeline outcomes to SP1 `success | denied | failed | pending-approval`, with
  unknown outcomes mapped to `failed`.
  - It passes SP1's allowlisted metadata: `inputHash` without its `sha256:` prefix, `fingerprint`,
    `errorCode`, `toolId` and `runId`.
  - Values SP1 would refuse are dropped.
  - Tool audits now include `runId`.
