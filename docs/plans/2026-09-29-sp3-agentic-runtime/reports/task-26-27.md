## Task 26: voice composition

**`createVoice({ models, realtime? })`** (`packages/agents/src/voice/create-voice.ts`):

- It returns a `CompositeVoice` built on the model factory's `transcription` and `speech` roles.
  In `AI_MODE=fake` those are the fake voice models.
- It also returns `transcribe` and `synthesize`. The routes need the duration and the media
  type, and `CompositeVoice.listen` and `speak` drop both.
- `capabilities` is `{ transcription, speech, realtime }`.
- It returns `null` when no voice model is configured, which turns the feature off.

**Realtime** is optional:

- SP3 pins no realtime provider.
- `realtime` is `false` unless SP4 injects a `MastraVoice` realtime provider.
- I did not add `@mastra/voice-openai-realtime`.

**Finding: `CompositeVoice` does not accept our models.** In `@mastra/core` 1.71,
`CompositeVoice` wraps AI SDK models only with `specificationVersion` `v2` or `v3`. The factory
builds `v4` models (AI SDK 7).

- A probe (`new CompositeVoice({ input: fakeTranscription }).listen(...)`) failed with
  `this.listenProvider.listen is not a function`.
- So each role goes through its own `MastraVoice` subclass: `AiSdkTranscriptionVoice` and
  `AiSdkSpeechVoice`. They call `transcribe` and `generateSpeech` from `ai` 7.
- This follows the precedent of `embedding-model-v3.ts`.

**Routes** (`voice-routes.ts`):

- Both are `registerApiRoute` routes with `requiresAuth: true`. `FirebaseMastraAuth` requires a
  verified member with `core.chat.use`.
- They live outside the API prefix, so neither the route allowlist nor the context middleware
  applies. SP4 reaches them through `/v1`.

`POST /voice/transcriptions` takes the raw audio body:

- **Accepted types:** webm, ogg, mp4, wav, x-wav and mpeg. Codec parameters are allowed.
- **Size:** at most 5 MB. The handler reads the stream with a cap and answers 413
  `PAYLOAD_TOO_LARGE` when it is exceeded.
- **Duration:** at most 60 s. A WAV is measured from its header before the model runs. Other
  containers are measured by the duration the model reports afterwards. Either way, a long clip
  answers 422 `AUDIO_TOO_LONG`.
- **Other errors:**
  - 415 `UNSUPPORTED_MEDIA_TYPE`;
  - 400 `VALIDATION_FAILED` for an empty body;
  - 503 `FEATURE_UNAVAILABLE`;
  - 502 `UPSTREAM_UNAVAILABLE`. The provider's message goes to the log only.
- The response is `{ data: { text, language, durationInSeconds } }`.

`POST /voice/speech` takes a strict `{ text (1–4000), voice? }`:

- It streams the audio with `cache-control: no-store`.
- The media type is sniffed from the bytes: WAV, Ogg, MPEG, WebM or MP4.
- It answers 503 when speech is not configured.

**Wiring.** `RuntimeParts.voice` holds the voice and `RuntimeParts.apiRoutes` holds both routes;
`apps/mastra` already passed `apiRoutes` through. Decision 0021 has a new amendment.

**Body limit.** Mastra's `bodySizeLimit` (4.5 MB by default) does not apply to custom routes. I
confirmed it in the built server:

| Upload | Result |
|---|---|
| 4.9 MB | 200 |
| 5.3 MB | our own 413 |

So `buildServerConfig` was left unchanged, and both handlers cap their own bodies. The speech
cap (64 KiB, else 413) came in a follow-up commit, `fix(agents): cap the speech request body`,
because the first version buffered `request.json()` without a limit.

`stacks/ai/openai.md` agrees with the role defaults: `gpt-transcribe` for transcription,
`gpt-4o-mini-tts` for speech, `gpt-realtime-2.1` for realtime. For realtime in the browser it
recommends WebRTC with a backend-issued ephemeral key; that is SP4's to wire.

## Task 27: scorers, datasets and eval runner

**Scorers.** They are built with `createScorer` from `@mastra/core/evals`, not `@mastra/evals`
(ADR 0004 E4). All are `type: "agent"` and read `run.output` through `agent-run-view.ts`.

| Scorer | Score | Not scorable |
|---|---|---|
| `tool-routing` | Share of `expectedTools` called. It counts subagent calls from `subAgentToolResults`, and the command of a delegation suspended for approval from `suspendedTools`. Names are compared sanitized, and `command.*` is a prefix pattern. Any `forbiddenTools` call scores 0. | No expectations |
| `citations-grounded` | Share of the `[kb:…]` markers that the run retrieved. A delegation counts only through its subagent's tool results. When citations were expected and none were written, the score is 0. | No citations expected or written |
| `tenant-leak` | 1 when no marker of another tenant appears in the answer or in any tool result, else 0. Markers come from the scorer options and the case. | No markers |
| `format-compliance` | Share of four checks: an answer or a pending approval; ≤ 4000 characters; no fake-directive or prompt residue; well-formed citation markers. | — |
| `faithfulness-judge` | LLM judge on the judge role: the supported share of the answer's claims, against the retrieved evidence plus the case reference. | No answer or no evidence |

- `faithfulness-judge` runs in real mode only. The fake model answers any JSON schema, so its
  verdicts would mean nothing. It is unit-tested with a scripted `MockLanguageModelV4`.
- `createCoreScorers` builds the set. `composeAgentRuntime` registers it in
  `RuntimeParts.scorers`, which `new Mastra({ scorers })` already receives; the judge is included
  only in real mode.

**Datasets** live in `packages/agents/evals/datasets/`, one JSON case per line:

| File | Cases |
|---|---|
| `assistant.v1.jsonl` | 18 |
| `knowledge.v1.jsonl` | 12 |
| `data.v1.jsonl` | 11 |
| `action.v1.jsonl` | 10 |

- Each case has `id`, `input`, `expectedTools`, `forbiddenTools`, `expectCitations`, `reference`,
  `foreignMarkers` and `tags`. The case is parsed with `EvalCaseSchema`, and the expectations
  become the `groundTruth`.
- The cases cover:
  - knowledge questions with citations;
  - cross-tenant probes;
  - form rendering and entity listing;
  - confirmed commands, which suspend for approval;
  - negative cases: web not enabled, no command without confirmation, small talk.
- Directives are used only where no keyword rule applies: two `describeEntity` cases.

**Baselines** are `evals/baselines/<agent>.json`, shaped `{ scorer: { minimum, tolerance,
real? } }`:

- Fake runs are deterministic, so the fake band is `1 / 0`.
- The optional `real` band gives `pnpm evals:real` room for drift. For example, `tool-routing`
  has `0.9 / 0.1` in real mode.
- `evaluateGate` fails a mean below `minimum - tolerance`. The floor is rounded to 4 decimals. A
  baselined scorer with no score also fails.

**Harness** (`eval-harness.ts`). `buildEvalHarness({ mode })` builds a real
`composeAgentRuntime`, so the agents, tools, guardrails, skills and processors are the real ones.
Around it:

- **Ports:** fake access for an eval-tenant member, a fake projects port, and `settings` left at
  the defaults.
- **Knowledge:** the eval knowledge corpus. It has 8 generic workspace documents for the eval
  tenant and 4 look-alike documents of a second tenant, carrying markers and their own document
  ids. It filters by tenant and namespace like the Postgres use case, including the 0.3 floor,
  and embeds with the runtime's embedding model.
- **Storage:** in memory, with no memory attached. Single-turn cases need no thread, so the
  `X-Conversation-Id` requirement does not apply here.
- **Mastra:** a `Mastra` that also registers the subagents. Without that, `getAgent("knowledge")`
  would throw, because since Task 20 subagents are not entry agents.

Real mode validates the agent env like the app boot does. Without a provider key it skips
cleanly: `evals:real` run without keys reported 5 skipped.

**Runner** (`run-agent-evals.ts`). `runAgentEvals` does the following:

1. It calls `runEvals` with `target: mastra.getAgent(id)`, a fresh member request context per
   case and concurrency 4.
2. Every baselined scorer runs with its floor as the threshold, so `runEvals`' verdict matches
   the gate.
3. It gates the scorer means against the baseline.
4. It writes `app/.evals/<agent>.json` in fake mode and `<agent>.real.json` in real mode. The
   directory is git-ignored.

The report carries:

- per-case scores and a 300-character answer excerpt;
- per-scorer means and not-scorable counts;
- the gate result;
- snake_case `bigqueryRows` for `ai_observability.eval_runs`, which SP5 exports: `run_id`,
  `agent_id`, `dataset_*`, `ai_mode`, `scorer_id`, `mean_score`, the band, `gate_passed`,
  counts, `git_sha` and timestamps. `GITHUB_SHA` passes through turbo for this.

**Leak detection** (`leak-detection.eval.test.ts`). It swaps in a knowledge port without the
tenant filter. The knowledge gate then fails on `tenant-leak`, which proves the gate is not
vacuous.

**Seeding.**

- `seedEvalDatasets` creates one Mastra dataset per file version (`<agent>.v<N>`, target the
  agent) with the cases as items.
- An unchanged file is skipped by SHA-256. A changed file of the same version gets its items
  replaced, and Mastra versions them.
- `pnpm evals:seed` (root) → `pnpm -F @core/mastra evals:seed` runs the script against the Mastra
  PostgresStore. It needs `--confirm-env` outside local, like `db:init`.

**Fake model.** The knowledge agent now has a keyword rule: it searches with the request.
Supervisor delegations to `knowledge` therefore retrieve and cite, which they did not before.

**Scripts and CI.**

- Root scripts: `evals`, `evals:real`, `evals:seed`.
- The new CI job `evals` sets `APP_ENV=local` and `AI_MODE=fake`, runs `pnpm evals` and uploads
  `app/.evals/` as an artifact.

## Deviations and concerns

1. **The gate needs no Postgres.** The plan says the CI job has a Postgres service. The gate runs
   in memory instead, because the knowledge eval uses the corpus port rather than `ai.chunks_v1`.
   Row-level-security isolation of the knowledge base stays covered by the Postgres tests of
   Tasks 12 and 18. The CI job has no service container.
2. **`pnpm evals:seed` was not run against Postgres.** Docker Desktop stopped answering during
   this session: the daemon pipe was gone at about 16:05, and I did not start or stop it. The
   seeding logic is covered by `seed-datasets.test.ts` on `InMemoryStore`: create, idempotent
   rerun, and replace on change. The first real run should be `pnpm db:init && pnpm evals:seed`.
3. **The subagent eval sets use the eval harness's own `Mastra`.** It registers the subagents.
   The app's Mastra still serves only `assistant` and `ping`.
4. **The eval harness imports the test fixtures** `supervisor.fixture.ts` (`noteModule`) and
   `testing/*`. The harness is not exported from `@core/agents`; only the dataset, baseline and
   seed APIs are.
5. **The fake gate sits at 1.0 everywhere.** It catches any regression of the scripted runtime,
   but it measures routing, grounding, isolation and format, not answer quality. Answer quality
   needs `evals:real` with the judge; Task 28 and nightly runs cover it.
6. **Speech media type.** `/voice/speech` sniffs the media type from the bytes and falls back to
   the SDK's media type. Streaming is a single chunk, because AI SDK 7 `generateSpeech` is not
   streaming.
7. **Voice bypasses the usage ledger, the budget guard and the audit trail.** `transcribe` and
   `generateSpeech` produce no Mastra span, so no `usage.llm_calls` row, budget check or
   provider/model/cost record exists per voice call. That breaks governance "Terceirização de
   chamadas de IA". Follow-up #29.
8. **Audio is personal data leaving to OpenAI.** `compliance.md` is a template, so the
   conservative default applies. SP4 must clear the DPA, legal basis, training opt-out and region
   gate before exposing `/v1` voice. The kill switch exists: without a key or model the routes
   answer 503. Follow-up #30.
9. **Shared files.** Tasks 23–25 also touch `compose-agent-runtime.ts` (`RuntimeParts`: the
   `scorers` type, `voice`, `apiRoutes`) and the `index.ts` export list, so expect conflicts
   there on rebase. `pnpm evals:seed` against Postgres is follow-up #31.
10. **SP4 still has to do the following:**
   - expose `/v1` voice endpoints through the gateway, with contracts;
   - attach `runtime.voice` to the chat agents;
   - decide on realtime.
