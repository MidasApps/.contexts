## Task 20: supervisor and subagents with skills

**Agents.**

- `assistant` is the supervisor:
  - its versioned instructions are `assistant.v1.md`;
  - `maxSteps` is 8;
  - it has `requestContextSchema`, the `entry` guardrail profile and the tenant-scoped memory
    (`AgentFactoryDeps.memory`);
  - `agents` is a function of the request context.
- The subagents are `knowledge`, `data`, `action` and `web`:
  - they run the `delegated` profile, with `maxSteps` 6;
  - each has versioned instructions and `requestContextSchema`;
  - they are not served by Mastra directly, so `/api/agents/knowledge/*` answers 404. That is a
    behaviour change from Task 15.
- `AgentDefinition.role` decides the split. Module agents default to `subagent`. The Task 18 test
  agent declares `entry`.

**Tenant subagents.**

- The supervisor offers only the subagents in `agent-settings.enabledAgents`. It offers `web` only
  when the tenant also opted in to a web tool.
- Settings are read once per run. The settings port is still unwired (SP5), so an unreadable store
  means the core defaults: knowledge, data and action, never web or a module agent.
- `onDelegationStart` checks the same settings on the server. It also:
  - refuses memory ids other than the run's own. Subagents inherit the supervisor memory under
    `<resourceId>-<agent>`, and a model-supplied id could name another tenant's resource;
  - drops model-written instruction overrides. Mastra passes empty instructions through without
    replacing the subagent's own.

**Skills.**

- The core skills are `data-catalog` (new), `safe-actions` (new) and `knowledge-citations`.
- Each is loaded at boot with `validateSkillContent` and attached as an inline skill (no Workspace).
  `data` gets data-catalog, `action` gets safe-actions, `knowledge` gets knowledge-citations.
- `AgentModule.skills` must be named `<module>-…`. A tenant sees a module's skills only when it
  enabled that module.
- `apps/mastra` copies `packages/agents/skills` into `public/skills` before the build.

**Action agent.**

- Its commands are `AgentModule.commands` (`{ tool, targetContractId }`) plus one core command,
  `command.tenancy.CreateProjectInput`. That command:
  - uses a new `projects` port;
  - is bound in `apps/mastra` to SP1 `createProject`, which authorizes again and audits
    `PROJECT_CREATED`.
- It is a mutation, so Mastra emits `tool-call-approval` and executes only after approval.
- `catalog.renderForm` is now registered. It resolves forms from the commands.

**Fake mode.** `coreFakeRules` delegate as follows:

| Message | Delegates to |
|---|---|
| A confirmation | action |
| Create words or data words | data |
| Web words | web |
| A question | knowledge |

The data agent renders the form of the command whose target contract matches the word. The action
agent runs the first command tool with the quoted name.

**Server-owned run options.** The context middleware now also removes these options from run
bodies, so a caller cannot raise the step cap or switch approval off:

- `maxSteps`, `stopWhen`;
- `instructions`, `system`;
- `toolsets`, `clientTools`, `activeTools`, `toolChoice`;
- `requireToolApproval`, `delegation`;
- processors, `modelSettings`, `providerOptions`.

## Task 21: connectors store, secret store and `/v1` routes

**Contracts.**

- `connectors.CreateConnectorInput` is a discriminated union picked from `ConnectorSchema`.
- `connectors.UpdateConnectorInput` changes the name, status, tool policy and config.
- `connectors.SetConnectorSecretInput` carries the secret, which is pii `sensitive`.
- Six endpoints live under `/v1/organizations/{organizationId}/connectors`:
  - list (cursor pages) and create (201 with `Location`);
  - get, patch and delete (204) of one connector;
  - `PUT .../{connectorId}/secret`, write-only, 204.
- New audit actions: `CONNECTOR_CREATED`, `CONNECTOR_UPDATED` (field names only),
  `CONNECTOR_DELETED` and `CONNECTOR_SECRET_SET`.

**Services context `connectors`.**

- The use cases authorize with `core.connector.read` or `core.connector.write`.
- Beyond the schema, every endpoint host must be https, on the default port and inside
  `allowedHosts`.
- The server owns `id`, `tenantId`, `status`, `secretRef` and the audit fields.
- The Firestore repository:
  - stores `schemaVersion` and `updatedBy`;
  - converts Timestamps to ISO;
  - reads another tenant's document as missing.

**Secret stores.**

- Secret Manager (`@google-cloud/secret-manager` 7.1.1, loaded lazily) is used outside local. It
  creates the secret once, adds a version on each put and reads `latest`.
- The Firestore-emulator `local-secrets` store is used in local. It throws outside local.
- Deleting a connector deletes the document first, then the secret.

**Storage and wiring.**

- Security Rules deny `connectors` and `local-secrets`.
- New index: `tenantId + createdAt desc`.
- The web routes are wired in `runtime-routes.ts`.
- `apps/mastra` binds the `connectors` and `secrets` ports; they are no longer unwired.

## Task 22: OpenAPI, MCP client, browser and Postgres connectors

**SSRF guard (`url-guard.ts`).** A URL must:

- use https on the default port, with no credentials;
- name a DNS host: no IP literal, no single label, no `.localhost` or `.internal`;
- stay inside `allowedHosts` when there is one;
- resolve only to public addresses. Loopback, private, link-local (including `169.254.169.254`),
  CGNAT, ULA, multicast and IPv4-mapped addresses are refused, and DNS errors fail closed.

`guardedFetch` checks every redirect hop, at most 5.

**OpenAPI** (`@apidevtools/swagger-parser` 13.1.0, `openapi-types` 12.1.3):

- Only JSON specs are accepted, fetched through the guard (15 s, 2 MB).
- Specs are validated and dereferenced with `external: false`. Any `$ref` left unresolved is
  refused, because the parser would fetch it outside the guard.
- Each allowed operation becomes a `defineCoreTool`:
  - GET and HEAD are reads; everything else is a mutation that needs approval;
  - the input is a strict `{ path, query, body }` built with `z.fromJSONSchema` (it exists in Zod
    4.6.5);
  - requests go only to the first `servers` URL, which must be in `allowedHosts`;
  - the call has a 15 s timeout;
  - the answer is capped at 100 KB and wrapped as `<untrusted_api_response>`.

**MCP and browser** (`@mastra/mcp` 2.1.1, which peers `@mastra/core >=1.68`):

- One `MCPClient` per connector, with `allowedHosts` and our guard as its `fetch`.
- The Bearer token comes from the secret store, and the timeout is 30 s.
- Tools are filtered by `toolPolicy.allow`.
- `needsApproval` is decided per call:
  - `readOnly` tools of an `mcp` connector skip approval;
  - every `browser` tool asks.
- The client uses `listToolsetsWithErrors`: `listToolsets` silently drops a failing server.
- stdio is a local-only developer override.

**Postgres.** `guardConnectorSql` is the semantic guard with qualified `allowedRelations`. The
query runs `READ ONLY` with a 5 s statement timeout and a 100/1000 row cap, and the DSN host must be
public.

**Per-run resolution.** Connector tools are resolved per run from the server context, never from
body toolsets. Each agent sees a different slice:

| Agent | Connector tools |
|---|---|
| supervisor | read tools |
| action | every OpenAPI and MCP tool |
| data | Postgres tools |
| web | browser tools, only with `webTools.browser` |

- A tenant's connectors load once per 5 minutes; eviction disconnects the MCP clients.
- A connector that fails to load is left out of the run.

## Deviations and concerns

1. **Task 19 is deferred.** The action agent has one core command (`tenancy.CreateProjectInput`)
   until module commands exist. It uses Mastra's per-call approval only.
   - The approvals port (SP1 four-eyes) stays unwired. A permission flagged `requiresApproval`
     answers `APPROVAL_UNAVAILABLE`.
   - There is no idempotency store for commands: Mastra runs an approved call once, but a retry
     across processes is not deduplicated.
2. **The supervisor needs `X-Conversation-Id`.** It owns the memory, and Mastra refuses a memory run
   without a thread (500). `ask_assistant` (Task 24), evals (Task 27) and the gate must send one.
3. **Tool names are sanitized.** Once an agent has skills, Mastra sends tool names to the model
   sanitized (`catalog.listEntities` becomes `catalog_listEntities`), and stream chunks, approval
   chunks included, carry the sanitized name. SP4 and the gateway must match approvals by that name.
4. **Subagents are no longer directly reachable** (`/api/agents/knowledge/*` answers 404).
   Everything goes through `assistant`.
5. **Beyond the plan text.**
   - Server-owned run options are stripped in the middleware.
   - The core `CreateProjectInput` command and its `projects` port are new.
   - `guardConnectorSql` extends the services SQL guard.
   - The reindex Postgres test needed a 60 s timeout: the catalog grew, and the machine was busy.
6. **MCP and browser tools skip the core pipeline.** They have no per-call SP1 authorize and no
   audit entry. Their gates are the admin-owned connector, the allowlist, the tenant from the
   context and user approval.
7. **Connectors have gaps.**
   - OAuth for MCP (`MCPOAuthClientProvider`) is not wired: an `oauth` connector connects without a
     token.
   - YAML OpenAPI specs are refused.
   - The Postgres connector has no live-database test; its runner is covered with a fake.
8. **Wiring is partial.**
   - `ToolCallFilter` is on the `data` agent only.
   - The web agent has no Firecrawl tools yet (Task 23).
   - The cross-SP items are in `docs/plans/2026-09-29-sp0-app-foundation/follow-ups.md`, #24–#28.
9. **I swapped the shared emulator's rules during my tests.** The connectors rules test loads
   `firestore.rules` into the shared Firestore emulator, and `cleanup()` does not restore it. My
   worktree run loaded HEAD's rules plus the connector blocks, without SP2's uncommitted client
   rules, so concurrent SP2 e2e runs could have seen denials. At 14:41 I reloaded main's merged rules
   by running the same test from the main tree.
10. **The worktree install broke once.** `node_modules` got broken package links during parallel
    installs, and I reinstalled it. The main tree's `node_modules` got the new packages from
    `pnpm install`.
