## What was built

### `pnpm dev` (`app/scripts/dev.ts`, `@core/scripts`)

`app/scripts` is a new workspace package, `@core/scripts`, registered in `pnpm-workspace.yaml`. That way turbo lint, typecheck and test cover it. The entry files are `dev.ts` and `seed-local.ts`, and the logic lives in `src/`.

`dev.ts` needs `.env.local`; without it, it exits with the `cp` hint. It loads the file without overriding the shell. Then `runDevSession` runs these steps:

1. `docker compose --env-file .env.local up -d --wait`.
2. `node apps/functions/build.ts`, the full build with the manifest and link.
3. It starts `node apps/functions/build.ts --watch`. This is a new esbuild `context().watch()` mode that rewrites only `lib/index.js`.
4. It starts `firebase emulators:start --project demo-core [--import .firebase-data] --export-on-exit .firebase-data`. `--import` is passed only when the folder exists. Anything but a `demo-*` project is refused.
5. It waits for the Emulator UI, then for the Functions `healthz`. Only then does it start `turbo run dev --ui=stream --filter=@core/web --filter=@core/mastra`.
   - Why: in the first run, turbo started as soon as the UI answered. Next and Mastra then loaded the CPU while the Functions emulator was loading `lib/`, and the load failed with "Cannot determine backend specification. Timeout after 10000".
6. It polls web `/v1/health` and Mastra `/health` and prints the ready lines.

Binaries (`firebase-tools`, `turbo`, `next`) are resolved to their JS entry points and spawned with `process.execPath`. No shell and no `.cmd` shims are involved, so the same code runs on Windows and POSIX.

**Shutdown** (`src/dev/supervisor.ts`, `src/dev/process-tree.ts`):

- **POSIX.** Each child is `detached`, so it leads its own process group. A stop sends SIGINT to each group, waits a grace period, then SIGKILLs the survivors' groups.
- **Windows.** A console Ctrl+C already reaches every child, so the supervisor waits up to 30 s and then runs `taskkill /T /F` on any survivor.
- **Other stops on Windows** (SIGBREAK, or a child crashing) cannot be signalled gracefully. They first run `firebase emulators:export` explicitly and then kill.
- **Pub/Sub orphan.** Verified in the first Ctrl+C test: firebase-tools starts the Pub/Sub emulator through a shell, and on Windows its `java.exe` survived the clean shutdown and kept port 8085. `dev.ts` now snapshots the emulator process tree once everything is up. After the stop it kills any snapshot process still alive whose pid and name both match.
- A second Ctrl+C forces the stop. Postgres keeps running on purpose: it is a compose service, and `docker compose stop` stops it.

Desktop is opt-in through the new root script `dev:desktop` (`pnpm -F @core/desktop tauri:dev`).

### `WEB_PORT` (apps/web)

`next dev` reads `PORT`, and so does Mastra. Both run under one turbo process with one env. So web now runs `node scripts/next-dev.ts`, which does the following:

- loads `app/.env.local`;
- validates `WEB_PORT` with `resolveWebPort`, default 3000, error names the variable;
- spawns `next dev --port N`.

The turbo `dev` task passes `WEB_PORT` through. The previous `seed:local` turbo task was removed; the root script runs the seed directly.

### `pnpm seed:local` (`app/scripts/seed-local.ts`)

- `resolveSeedTarget` (Zod) requires the following, and `UnsafeSeedTargetError` (`UNSAFE_SEED_TARGET`) names the variables, never their values:
  - `APP_ENV=local`;
  - a `demo-*` `FIREBASE_PROJECT_ID`;
  - a loopback `FIREBASE_AUTH_EMULATOR_HOST`;
  - a `SEED_OWNER_PASSWORD` of 6+ characters. Empty means unset, so the local-only default `demo-owner-password` applies.
- `upsertOwnerUser` works through the `AuthAdmin` port:
  - it looks up the user by email and creates `owner@demo.local` if missing (verified email, display name "Demo Owner");
  - otherwise it resets password, name and verified flag;
  - it reports `created` or `updated`.
- `createAuthEmulatorAdmin` implements the port over the Auth Emulator REST API. It calls `projects/{id}/accounts`, `accounts:lookup` and `accounts:update` with `Bearer owner` and a 10 s timeout, parses responses with Zod, and turns emulator errors into `AuthEmulatorRequestError` with the emulator code.
- The extension point is `src/seed/seed-steps.ts`, with `LOCAL_SEED_STEPS = [ownerUserStep]`. SP1 appends its organization, project and role steps there.

## Deviations and notes

- **`app/scripts` is a workspace package** (`@core/scripts`), so its tests and lint run in turbo. It is not a boundaries element: it imports no workspace package.
- **The Functions watcher runs outside turbo,** before the emulators. Its `dev` script (`node build.ts --watch`) still exists for standalone use, but `pnpm dev` does not use it.
- **Readiness defaults duplicate the servers' own:** web 3000 and Mastra 4111 in `readDevPorts`. The region `southamerica-east1` is duplicated in `dev.ts` with a sync comment. Neither can be imported from the other package without coupling.
- **Seed output** uses plain `process.stdout` lines (CLI output), like the catalog scripts. It is not the JSON logger.
- **The owner uid is emulator-generated.** It stays stable across runs through `.firebase-data` export and import. After deleting `.firebase-data`, a new uid is created.
- **`pnpm audit` currently reports 2 moderate advisories** and no high ones, so the CI audit step passes.

## Review fixes (Spec PASS / Quality APPROVED, minors)

Commits: `6fef895` fix(workspace): harden dev shutdown and fail fast on busy ports; `0dacc41` ci(workspace): compare the framework guard against the event base; plus the docs commit that adds this section.

1. **Process identity.**
   - `ProcessEntry` gains `startedAt`:
     - Windows: `Win32_Process.CreationDate`, as UTC ISO;
     - POSIX: `ps -o lstart=` with `LC_ALL=C`.
   - `findSurvivors` requires pid, name and start time to match, and never reports an entry whose start time is unknown.
   - Tests cover a reused pid of a same-name process, the lstart parse and the CIM JSON parse. They were red first, 4 failing.
2. **Snapshots at shutdown.**
   - The firebase CLI pid is recorded as soon as it is spawned.
   - The stopper re-snapshots its descendants when a stop begins and unions that with the startup snapshot through `mergeSnapshots` (tested). Ancestry comes from `collectDescendants`, and survivors are still filtered by start time.
   - Stopping during startup is handled in three places:
     - every wait aborts;
     - `startLongRunning` returns before any further start;
     - `supervisor.start` throws once a stop has begun (test red, then green).
3. **Busy ports.** Before anything starts, `pnpm dev` checks `WEB_PORT` and the Mastra `PORT`.
   - `port-check.ts` tries a wildcard bind first, then connects to `127.0.0.1` and `::1`. The order matters: the first version ran them in parallel and connected to its own bind probe.
   - `describePortConflicts` in `dev-plan.ts` builds the message.
   - Tests use real listeners on loopback and on all interfaces, plus a free port.
   - Verified: with the unrelated server on :3000, `node scripts/dev.ts` prints `failed: port 3000 (web) is already in use; stop what holds it or set WEB_PORT to a free port` and exits 1 before compose.
4. **CI guard.** The step compares against a base chosen by event, passed through `env`, not interpolated into the script:
   - `pull_request`: `github.event.pull_request.base.sha`;
   - `push`: `github.event.before`, and the step exits 0 with a notice when that is the all-zero SHA;
   - otherwise: `origin/main`.

   It fails with `::error::` and a `--stat`. The script was exercised locally: push base `main` gave exit 0, an all-zero base skipped, and the root commit as base failed. actionlint 1.7.12 exits 0.
5. **`startLongRunning`** takes one named object: `{ supervisor, stopper, config, bins, tracker }`. `createStopper` does too.
   - `parsePort` stays duplicated, with a note at both sites (`scripts/src/dev/dev-plan.ts`, `apps/web/scripts/web-port.ts`). Sharing it would need a package both import, and the only candidates, `@core/services` and `@core/contracts`, are runtime code.
